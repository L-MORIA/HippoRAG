## 5. Аутентификация — отдельный разбор (предмет проверки)

### 5.1 Как реализована

`src/hipporag/search_api/server.py`:

```python
API_KEY = os.getenv("API_KEY")                     # строка 33 — читается один раз при импорте

@app.middleware("http")                             # строка 91
async def api_key_guard(request: Request, call_next):
    """Опциональная аутентификация: при заданном API_KEY требуется заголовок X-API-Key."""
    if API_KEY and request.headers.get("X-API-Key") != API_KEY:
        return JSONResponse(status_code=401, content={...})
    return await call_next(request)
```

CORS (строки 82–88): `allow_origins=["http://localhost:3000", "http://localhost:8000"]`, `allow_credentials=True`, `allow_headers=["Content-Type", "Authorization"]`.

### 5.2 Эксперимент (реальный `server.py`, 16 сценариев)

| Сценарий | `API_KEY` не задан | `API_KEY` задан |
|---|---|---|
| `GET /health` без ключа | **200** | **401** |
| `GET /health` с неверным ключом | **200** | **401** |
| `GET /health` с верным ключом | **200** | **200** |
| `GET /docs` без ключа | 200 | **401** |
| `GET /openapi.json` без ключа | 200 | **401** |
| `POST /ingest` без ключа | 200 | **401** |
| `POST /search` без ключа | 200* | **401** |

\* 500 в части сценариев — артефакт моей заглушки (`HippoRAG.rag_qa` в реальном коде присутствует, `src/hipporag/HippoRAG.py:638`), а не дефект проекта.

**Что работает правильно:** защита единая для всех маршрутов, включая `/docs`, `/openapi.json` и файловый загруз `/ingest`; ключ не пишется в логи; при заданном ключе подбор переборами ничего не даёт — 401 без ключа и с неверным ключом.

### 5.3 Дефекты

**D1 — блокирующий: CORS запрещает сам заголовок, который требует сервер.** Сервер требует `X-API-Key`, но `allow_headers` содержит только `Content-Type` и `Authorization`. Прогон preflight:

```
OPTIONS /search
  Access-Control-Request-Headers: content-type,x-api-key
→ 400 Bad Request
  access-control-allow-headers: Accept, Accept-Language, Authorization, Content-Language, Content-Type
```

`x-api-key` в разрешённых заголовках отсутствует → CORS-слой отклоняет preflight, браузер блокирует запрос. **С верным ключом браузерный клиент всё равно не может его отправить.** Это ровно тот сценарий, ради которого в конфигурации и прописаны origin'ы `localhost:3000`/`localhost:8000`.

**D2 — порядок middleware: guard отвечает на preflight раньше CORS.** Guard добавлен последним → он внешний. Preflight **без** ключа возвращает 401 вместо CORS-ответа (`access-control-allow-origin` отсутствует), то есть браузер не получает и CORS-метаданные.

**D3 — режим fail-open по умолчанию.** При незаданном `API_KEY` API **полностью открыт**: `/search`, `/ingest` (загрузка файлов), `/docs`, `/openapi.json`. Плановый §8.5 это прямо называет («при `API_KEY` не задан API открыт всем, кто достучался»), но в списке задач H0–H3 **задачи на этот риск нет** — он числится «известным», а не «закрытым».

**D4 — сравнение не констант-таймовое.** `!=` вместо `secrets.compare_digest`. Низкий практический риск, но для значения, принимаемого как секрет, корректнее constant-time.

**D5 — нет наблюдаемости и ротации.** 401 не логируются и не считаются; `API_KEY` читается один раз при импорте → смена ключа требует рестарта процесса; нет поддержки нескольких ключей, Bearer-токенов, ролей и ограничения по источнику.

**D6 — аутентификация не документирована.** `.env.example` в репозитории **отсутствует** (план сам называет его пробелом в §8.5), а `API_KEY`/`X-API-Key` **не упоминаются ни в `README.md`, ни в `README_RU.md`, ни в `docs/HOW_TO_RUN.md`** — только в аудиторских отчётах и в самом плане. Пользователь не узнает о ключе из пользовательской документации.

**D7 — риск-контекст плана устарел: репозиторий снова публичный.** §13 (строка 2418) выводит приватность данных из «приватного репо». Коммит 02.11 делал репозиторий приватным, 03.11 он **снова публичный** (`visibility: public` в API) — иначе Actions/billing не проходит, что и зафиксировано в §0.1. Сама гигиена данных при этом в порядке: в дереве **0 PDF**, **0 `.env`**, только публичные датасеты `reproduce/dataset` (47 МБ). Но «приватный репо» как контроль риска больше не действует, и **fail-open аутентификация становится единственным барьером между публичным репозиторием и открытым API**.

### 5.4 Вердикт по аутентификации

**Функционально — соответствует плановому описанию; как продукт — не готова к выдаче наружу.** Механизм работает ровно так, как описан в §8.5, но (а) не документирован, (б) не имеет режима «обязателен», (в) **ломает единственный сценарий, для которого и написан** — браузерный клиент с включённым ключом. Минимальный фикс — три строки: добавить `X-API-Key` в `allow_headers`, вынести guard **внутрь** CORS (порядок middleware) и задокументировать ключ в `.env.example` + `HOW_TO_RUN.md`.

2. **Внутреннее противоречие плана по publish-job:** §0.1 утверждает, что job удалён (`766f189`), а §14 (строка ~2650) — что job «недостижим, но существует». 3. **Устаревшие счётчики в §0.1/§1.1:** «7 модулей / 12 payload-сайтов» (факт 9/21), «96 тестовых функций (115 кейсов)» (факт 191 функция, 207 кейсов в CI). Инварианты актуальны, цифры — нет.
4. **`paths-ignore: ['docs/**', '**/*.md']` в CI.** Docs-only PR не порождают статус-checks → не примут внешнего контрибьютора и не проверяются. Отдельно: провалы прогонов #35/#36 на docs-коммитах (08:09 и 08:23) вызваны **не** этим правилом, а блокировкой Actions по биллингу на приватном репо (все джобы — 0 с); после возврата репозитория в публичный режим и переписывания workflow прогоны зелёные. То есть после 03.11 docs-only коммиты перестали запускать CI вовсе — это отдельный, до сих пор не закрытый риск.
