### 2.1. Поправка к формулировке рецензии

Утверждение «путь `main.py --rag_type standard` на этапе QA сломан» **к этому
репозиторию не относится**: `main.py` — тонкий фасад над `astro_app.cli`,
аргумента `--rag_type` в нём нет, а `StandardRAG` в продуктовом коде не
используется (в пакете `hipporag` — только в `llm/__init__.py` и в докстринге
`config_utils.py:308`).

Это не уменьшает ценность R-1…R-4: это **реальные дефекты публичного API
пакета `hipporag`** (`pip install hipporag` → `StandardRAG.qa()` падает с
`AttributeError`). Но на **продуктовые пути astro_app** (HippoRAG / LM Studio)
они не влияют: влияние на пользователя продукта нулевое, на потребителя
пакета — прямое. Правки внесены в любом случае.

## 3. Решение владельца о режиме по умолчанию

**Подтверждено владельцем 04.11.2026:** режимом по умолчанию стал
**режим 5 «BM25+CE-ru»**, рекомендованы **2 и 5**.

Условие владельца — «если он лучше старого дефолтного режима 2 по всем
показателям». Проверка по измеренным данным:

| Показатель | Режим 5 | Режим 2 | Кто лучше |
|---|---|---|---|
| recall@5 (документы) | 97,5 % | 95,0 % | **5** |
| recall@5 (страницы) | **65,0 %** | 60,0 % | **5** |
| MRR@10 (страницы) | **0,520** | 0,477 | **5** |
| p95 | **225 мс** | 661 мс | **5** |
| MRR@10 (документы) | 0,902 | **0,913** | 2 (минимально) |
| nDCG@10 (документы) | 0,921 | **0,928** | 2 (минимально) |

**Честная оговорка.** Режим 5 выигрывает не по каждому числу: по документным
MRR@10 и nDCG@10 режим 2 минимально лучше. Разница — **в пределах разрешения
выборки**: 40 вопросов дают шаг 2,5 п.п., то есть это 1 вопрос из сорока, а не
статистически значимый разрыв. Приёмка H1-2 («default не хуже лучшего режима на
80 % eval-запросов; p95 ≤ 10 с») при этом выполнена: по рабочей страничной
метрике режим 5 впереди, по латентности — втрое быстрее, бюджет 10 с
выполнен с запасом 9,8 с. Именно поэтому режим 2 **остаётся рекомендованным
вторым**, а не «проигравшим».

Цена решения — RU cross-encoder `DiTy/cross-encoder-russian-msmarco` (~700 МБ,
первый запуск качает модель). Чтобы деградация не была тихой, она сделана
явной (п. 4.2, Н-3).

### 5.1. Что поймал CI на первом прогоне

Первый прогон CI (`41877623822`, коммит `b1f40aa`) дал **6 зелёных из 7**:
красным оказался `Test Suite (windows-latest)`. Разбор лога: тест
`test_repo_baseline_file_is_utf8_lf_with_final_newline` проверял байты
**рабочего дерева**, а на windows-раннере git с `core.autocrlf=true`
переводит LF в CRLF при checkout'е. То есть тест ловил не дефект
репозитория, а особенность checkout'а — **дефект был в самом тесте**.

Исправлено: проверяется содержимое **blob'а в git** (`git show HEAD:<путь>`),
а при недоступности git — рабочее дерево с нормализацией переводов строк.
Логика проверена в трёх сценариях: blob с LF при CRLF в рабочем дереве —
проходит; дерево без git — проходит; **настоящий CRLF, закоммиченный в
blob'е, — по-прежнему ловится**.

## 6. Ограничения — что проверено, а что нет

* **Индекс `outputs/astrology_test` в репозитории отсутствует.** Числа
  p50/p95/recall/MRR/nDCG **независимо не воспроизведены**: проверялась
  внутренняя согласованность чисел с кодом и с отчётами. Это ограничение
  унаследовано от H1-1/H1-3 и не закрыто этим раундом.
* **Cross-encoder `DiTy/cross-encoder-russian-msmarco` (~700 МБ) локально не
  установлен.** Поведение режима 5 **с** работающим CE не проверялось —
  проверена только ветка деградации (Н-3).
* **`outlines` локально не установлен**, а в extra `offline` он не входит —
  поэтому в CI модуль `hipporag.llm.transformers_offline` не импортируется, и
  S-4 проверен **по исходнику**, а не импортом. Функциональная проверка
  потребует `pip install -e ".[offline]"`.
  **Уточнение от 04.11.2026 (раунд 7):** проверка «по исходнику» не покрывает
  работоспособность бэкенда. Функциональная проба на настоящей мини-модели
  (`sshleifer/tiny-gpt2`) показала, что `TransformersOffline.infer()` падал и
  после правок S-4: промпт строился как батч (N-1), free-form `batch_infer`
  утекал промпт в ответ (N-2), а `infer()` возвращал двойку вместо тройки (N-4).
  Плюс `retrieve([QuerySolution(...)])` падал с `TypeError: unhashable type`
  (N-3). Все четыре закрыты в раунде 7 — отчёт
  `docs/AUDIT_OFFLINE_BACKEND_FIX_2026-11-04.md`. Вывод «S-4 закрыто» в этом
  документе следует читать как «три заявленных дефекта S-4 устранены», а не как
  «offline-бэкенд работоспособен».
* **`isort` удалось поставить локально** (8.0.1) — проверка порядка импортов
  пройдена локально, а не только на стороне CI.
* **Правки R-1…R-4 лежат в `src/hipporag` — вне продуктовых путей
  astro_app** (HippoRAG / LM Studio). Их влияние на пользователя продукта
  нулевое; на потребителя `pip install hipporag` — прямое (было: падение
  `StandardRAG.qa()`).
* **`black` на этой машине зависает при пуле процессов** — обход: `--workers 1`.
  Это особенность окружения, а не дефект кода.
