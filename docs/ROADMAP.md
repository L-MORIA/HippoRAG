## P0 — процесс: перенести pre-commit-хук в репозиторий

### Задача P0-1. Версионируемый хук вместо локально сгенерированного

**Проблема.** Сейчас работает так: `.pre-commit-config.yaml` лежит в репозитории, а сам хук —
`.git/hooks/pre-commit` — генерируется командой `pre-commit install` **локально** и в git не попадает.
Следствие: после свежего клона `git commit` не запускает ни одной проверки, пока разработчик
не вспомнит про `pre-commit install`. Проверено: `docs/CONTRIBUTING.md` об этом предупреждает,
но механизма, который не даёт забыть, нет.

**Цель.** Сделать так, чтобы содержимое хука жило в репозитории и проходило ревью в PR.

**Шаги.**

1. Создать каталог `.githooks/` и в нём исполняемый файл `.githooks/pre-commit`:
   ```bash
   #!/usr/bin/env bash
   set -euo pipefail
   exec python -m pre_commit run --hook-stage pre-commit "$@"
   ```
   Прямой вызов `python -m pre_commit` вместо `pre-commit` — чтобы не зависеть от того,
   в какой интерпретатор попал CLI при `pip install`.
2. Проставить исполняемый бит в индексе git: `git update-index --chmod=+x .githooks/pre-commit`
   (иначе после клона на Linux/macOS файл будет неисполняемым, и git молча пропустит хук).
3. Переключить локальный путь хуков: `git config core.hooksPath .githooks`
   (это **локальный** git-конфиг — в репозиторий он не попадает, см. «Честно о границах»).
4. Обновить `docs/CONTRIBUTING.md`: заменить шаг `pre-commit install` на
   `git config core.hooksPath .githooks` (+ `pip install -e ".[dev]"`).
5. Проверить, что `pre-commit install` больше не нужен и не конфликтует: удалить старый шим
   (`pre-commit uninstall`), убедиться, что `git commit` по-прежнему запускает проверки.

**Приёмка.**
- `git commit` с намеренно плохим кодом (например, `import os` без использования) **отклоняется**;
- `ls .git/hooks/pre-commit` → отсутствует, а `ls .githooks/pre-commit` → присутствует и исполняем;
- `git ls-files -s .githooks/pre-commit` → режим `100755` (исполняемый);
- `pre-commit run --all-files` → 12/12 Passed.

**Оценка:** 30–40 минут.

### Честно о границах этого решения

`core.hooksPath` — это **локальная настройка git**, она не переносится при клонировании
ровно так же, как не переносится сгенерированный `pre-commit install` шим.
Автоустановки хука не будет ни в одном из вариантов. Что реально меняется:

| | Сейчас (`pre-commit install`) | После (`core.hooksPath`) |
|---|---|---|
| Где лежит скрипт | `.git/hooks/` — локально, генерируется | `.githooks/` — **в репозитории**, под ревью |
| Видно в PR / в `git log` | нет | да |
| Зависит от версии pre-commit на машине | частично | нет (пин в `rev:`) |
| Шаг после клонирования | `pre-commit install` | `git config core.hooksPath .githooks` |
| Кто отвечает за содержимое скрипта | инструмент | репозиторий (нужно ревьюить правки `.githooks/`) |

**Дополнение (рекомендуется):** CI-job, который прогоняет `pre-commit run --all-files` на
всей ветке. Тогда забытый хук в локальном клоне не приведёт к «зелёному» PR — CI всё равно
проверит. Это закрывает ту же дыру, но с другой стороны (на сервере), и не требует
распространять скрипт в репозитории.

**Альтернатива, если владелец не хочет никаких ручных шагов:** оставить `pre-commit install`
и добавить только CI-job из абзаца выше — тогда установка хука остаётся необязательной
оптимизацией, а не условием прохождения PR.

### Задача P1-4. Нормировать CE-скоры перед смешиванием (режимы 3–6)

**Состояние.** `_rerank_with_crossencoder()` и `_rerank_with_crossencoder_ru()` (`main.py:445,467`)
смешивают **несоизмеримые шкалы**:

```python
final = xc * 0.7 + old * 0.3 * (1.0 + boost)
```

- `xc` — сырой выход CE: EN-модель `ms-marco` отдаёт **логит** (диапазон 7.86…8.84 при std 0.21),
  RU-модель `DiTy/cross-encoder-russian-msmarco` — **вероятность** (0.001…0.88);
- `old` — embedding-скор × boost: диапазон 1.84…13.77.

Измерено на 50 кандидатах одного запроса (2026-11-02):

| Ветка | Доля CE-части в `final` | Разница CE между релевантными и нерелевантными |
|-------|--------------------------|--------------------------------------------------|
| EN (режимы 3, 4) | **85.6 %** | **+0.086** — на русском тексте почти шум |
| RU (режимы 5, 6) | **3.1 %** | +0.0705 (нормальная шкала 0…1) |

То есть коэффициенты «0.7 / 0.3» не означают ничего: EN-режим живёт на 86 % сигнала, который
на русском тексте релевантность почти не различает (прямое доказательство: нерелевантный чанк
получил `xc=8.83`, релевантный — `xc=8.26`), а RU-режим, наоборот, CE практически игнорирует.

**Что сделать.** Нормировать `xc` через `min_max_normalize()` из `hipporag.utils.misc_utils`
(он **уже импортирован** в `main.py:15` и уже применяется там же к `dpr_scores` в строке 370;
констант-распад обработан — возвращается `ones`).

```python
from hipporag.utils.misc_utils import min_max_normalize
...
xc_norm = min_max_normalize(np.array([float(s) for s in xc_scores]))
final = xc_norm * 0.7 + old * 0.3 * (1.0 + boost)
```

**Оценка влияния (проверено A/B на 3 запросах, 2026-11-02).** Топ-5 **не изменился**
(5/5 → 5/5, 2/5 → 2/5, 5/5 → 5/5) — на текущем корпусе выдачу определяет embedding + keyword-boost.
Поэтому задача **латентная**: дефект ударит по запросам с перефразировкой, где нет буквального
keyword-совпадения и решать должен именно CE. Правка 2 строки, но требует замера на более
широком наборе запросов (см. P1-2).

**Приёмка.** (1) Доля CE-части в `final` перестаёт зависеть от модели и равна ~70 % в обеих
ветвях; (2) на наборе из P1-2 (ground truth + `recall@k`) нормированная формула **не хуже**
текущей ни в одном запросе; (3) для EN-режима — либо использовать CE-ru, либо явно пометить
режим как «английский» в меню (уже помечен: `3 — BM25 + Embedding + CE (English)`).

**Оценка:** 30 мин кода + время на замер (P1-2).

### Задача P1-5. Двуязычное распознавание и ответ (RU по умолчанию, EN — отдельная опция)

**Требование владельца (2026-11-02):** запросы будут **в первую очередь на русском языке**;
исправить нужно именно функцию распознавания/ответа — сделать её **универсальной на 2 языках**;
**если в меню нет отдельной опции этого метода для распознавания и ответа на русском — добавить**.

**Основание — замер режимов 1, 2, 3 на запросе «какие книги написала Максимова И.В.?» (2026-11-02).**

| Режим | Время | Топ-1 | Релевантных в топ-10 | Итог |
|-------|-------|-------|---------------------|------|
| 1 — Multi-vector | 12.6 с | **нерелевантный** (чанк про астероид Хирон) | 2 (позиции 1, 2) | ❌ хуже всех |
| 2 — Граф | 0.6 с | ✅ «Психологический фэншуй» | 9 (1,2,3,5,6,7,8,9,10) | ✅ **лучший** |
| 3 — BM25+CE-en | ~10 с | ✅ «Психологический фэншуй» | 8 | ✅ работает (см. P1-4) |

**Найденный дефект режима 1 — то, что нужно чинить.**
`reformulate_query()` (`main.py:179-237`) — единственный «распознающий» компонент, используется
**только** режимом 1 (`main.py:289`). Его system-промпт жёстко русский и доменно-специализированный:

> «Ты — эксперт по астрологии и фэншуй. Улучши поисковый запрос: выдели ключевые термины
> (знак зодиака, планета, зона дома, действие). Ответь ОДНИМ предложением (3-10 слов). Без пояснений.»

На запрос про книги Максимовой LLM ответил **отказом**: «Запрос не содержит астрологических или
фэншуй-терминов для улучшения.» Этот мета-ответ без всякой проверки пошёл в эмбеддинг:

- `kw: +0.00` у **всех 10** результатов — keyword-boost по термам «не содержит / астрологических /
  фэншуй» не совпал ни с одним чанком корпуса;
- релевантная книга упала на **позицию 2**, на позицию 1 встал нерелевантный чанк.

Вывод: доменная специализация промпта **ломает даже русские** запросы вне астрологического домена.

**Что сделать.**

1. **Валидация ответа LLM** (независимо от языка, чинит найденный дефект): если ответ пуст,
   содержит мета-формулировки («не содержит», «запрос», «улучшен», «no », «does not contain») или
   не выглядит поисковым запросом → **отбросить, вернуть исходный запрос**.
2. **Двуязычный `reformulate_query(query, lang)`** — два системных промпта:
   - **RU (по умолчанию)**: нынешний доменный + явное правило «если доменных терминов нет —
     верни исходный запрос без пояснений»;
   - **EN**: английский аналог с доменными терминами на английском (sign, planet, house zone).
3. **Определение языка** — детектор по доле кириллицы, без новых зависимостей:
   `cyrillic_ratio > 0.3` → RU, иначе EN; язык переопределяется флагом в меню.
4. **Ответ на языке запроса** — в `HippoRAG.qa()`:
   - `prompt_user` сейчас жёстко русский: `"Вопрос: " + question + "\nМысли: "`
     (`HippoRAG.py:932`) → сделать двуязычным;
   - шаблон: `rag_qa_astrology` (RU) + **новый `rag_qa_astrology_en`** (EN) с маркерами
     `Thoughts: ` / `Answer: `;
   - **парсер ответа уже двуязычный** — `HippoRAG.py:969-975` понимает и `Ответ:`, и `Answer:`;
     менять не нужно;
   - выбор шаблона — **по языку запроса**, а не по `global_config.dataset`.
5. **Меню: добавить отдельную RU-опцию этого метода** (по критерию владельца). У режима 1 сейчас
   одна опция — в отличие от пары BM25 (3 = CE-en, 5 = CE-ru) и Small→Big (4/6). Вариант:
   `1` — авто-детект, `1R` — принудительно RU, `1E` — принудительно EN.

**Приёмка.**
- На наборе из P1-2 (RU + EN с ground truth) `recall@5` режима 1 **не хуже** текущего на RU
  (сейчас релевантная книга на позиции 2) и **> 0** на EN;
- meta-ответ LLM («Запрос не содержит…») **не попадает** в эмбеддинг — в логе видно
  `✅ Переформулировка` только с полезным запросом;
- на EN-запросе и поиск, и ответ LLM приходят на английском (маркер `Answer:` распознаётся);
- в меню присутствует отдельный пункт RU-варианта режима 1.

**Оценка:** 0.5–1 день (правка ~40 строк + шаблон EN + тесты). Связана с **P1-4**: там шкалы
CE-скоров в режимах 3–6, здесь — распознавание и ответ режима 1.

| Кнопка «Update fork» в UI | была | **нет** (связь с upstream разорвана на стороне GitHub) |
| `origin` = `osu-nlp-group/hipporag` (локально) | работал | **работает** — `git fetch origin` / слияние с upstream по-прежнему возможны |
| `fork` = `L-MORIA/HippoRAG` (локально) | работал | **работает** — fetch/push в порядке |
| GitHub Actions | безлимитные минуты для public | минуты из пула Free (≈2000/мес) — важно при частых прогонах |

**Почему GitHub отвязал репо.** Публичный форк публичного репозитория не может быть приватным:
видимость форка наследуется от upstream. GitHub API принимает команду, но переводит форк в
standalone-репозиторий, и на время операции отдаёт `403 Your repository is disabled` —
через несколько секунд доступ восстанавливается.

**Как вернуть связь с upstream (если понадобится):** удалить `L-MORIA/HippoRAG` и создать
форк заново (`gh repo fork OSU-NLP-Group/HippoRAG`), затем перенести коммиты. Либо оставить
как есть и работать с `origin` локально.

**Обратный путь в public:** для standalone-репозитория (не форка) правило «видимость форка
нельзя менять» не применяется, поэтому `gh repo edit --visibility public` должен быть
доступен. Фактически не проверялось — при необходимости проверить и вернуть обратно.

**Последствие для PR в upstream:** PR из приватного standalone-репозитория в публичный
upstream GitHub допускает (head-ветка указывается как `L-MORIA:<branch>`), но автоматической
связи «Update fork» больше нет — обновления надо забирать вручную через `git fetch origin`.
