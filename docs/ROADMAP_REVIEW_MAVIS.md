## 3. Неверный приоритет

### ⚠️ P0-1 (hooks path) — проблема переоценена, решение не оптимально

План подаёт P0-1 как **P0** (блокирующий). Аргумент: «свежий клон не запускает проверки».

**Возражения:**

1. `pre-commit install` после клонирования — **стандартный и документированный workflow**
   pre-commit. `CONTRIBUTING.md` уже предупреждает (план сам это признаёт).
2. Предлагаемое решение (`git config core.hooksPath .githooks`) — **тоже ручной шаг** после
   клонирования. Таблица «сравнения» в плане это честно показывает. Разница между двумя
   вариантами — косметическая: вместо одной команды разработчик выполняет другую.
3. **CI уже прогоняет те же инструменты** (black/isort/ruff/pytest в lint и test jobs).
   Если разработчик забыл хук — CI отловит. План упоминает CI-job как «дополнение»,
   но это должно быть **основным** решением: ноль ручных шагов, ноль новых файлов.

**Рекомендация:** приоритет P0 → **P2**. Основное решение — CI-job
`pre-commit run --all-files` (15 минут). `.githooks/` в репозитории — опционально.
Если владелец считает этот пункт критичным — можно оставить P1, но не P0: это не
«блокирует корректность или безопасность», а «улучшает DX».

## 4. Точечные замечания

### 4.1. P0-2: фикс теряет мультиисточники S-12 — нужно задокументировать

Фикс `_get_chunk_meta` берёт `m[0]` — первичный источник. Для **отображения в меню**
это корректно (нужен один source для строки «источник»). Но:

1. S-12 был именно о хранении **всех** источников чанка (два PDF с одинаковым
   колонтитулом → оба в цитате).
2. Полный список обрабатывается в ядре: `build_citation_from_metadata()` в
   `HippoRAG.py:576-580` → `Citation.sources` — все источники. Этот путь P0-2
   **не затрагивает**.
3. Но план не упоминает, что `citations[].sources` в API остаётся полным.

**Правка:** добавить в приёмку P0-2 пункт «`citations[].sources` в API по-прежнему
содержит все источники» + ссылку на `build_citation_from_metadata()`.

### 4.2. P1-4: `min_max_normalize` при 1 кандидате — вырожденный случай

`min_max_normalize` на массиве длины 1 (range=0) возвращает `ones` — все кандидаты
получают одинаковый CE-скор 1.0. Для `top_k=5` с отфильтрованным списком из 1–2
кандидатов нормировка вырождается. План не упоминает этот edge case.

**Правка:** задокументировать как известное ограничение, либо fallback на 0.5 при
`range == 0`. Проверка: код в `misc_utils.py:141-149` уже возвращает `ones` — это
обозначено, но не помечено как «известное ограничение для малых выборок».

### 4.3. P1-2: не учтены LLM-зависимые режимы

Метрики recall@k / MRR корректны для retrieval-режимов (2–8, 13–16, 20). Но режимы
1 (reformulate через LLM), 12 (Self-RAG ответ), 19 (GraphRAG ответ), 21 (DAT+LLM)
зависят от **состояния LLM** (LM Studio загружена/нет, недетерминизм даже при temp=0).
План не специфицирует, как сравнивать эти режимы «до/после».

**Правка:** в P1-2 добавить: для LLM-режимов замерить retrieval-часть отдельно
(до LLM-вызова), а LLM-ответы фиксировать без требования побитового совпадения
(структура + факты, не текст).

### 4.4. Порядок работ: P1-1 (vector stores) не должен идти рядом с P1-2 (качество)

План ставит P1-1 (подключить qdrant/chroma/milvus) на неделю 2 **вместе с** P1-2.

**Возражение:** это разные весовые категории. P1-2 — доказательство, что весь аудит
дал выигрыш. P1-1 — инфраструктурная замена, не влияющая на качество (тот же контент,
другой движок хранения). План сам признаёт: «интерфейс бэкендов не унифицирован по
метаданным». Выполнение P1-1 **до** P1-2 означает, что замер качества будет сделан
на ещё не устоявшемся хранилище.

**Правка:** P1-1 — **после** P1-2, когда есть метрики для сравнения «до/после» смены
бэкенда. И если бэкенды нужны, сначала унифицировать интерфейс метаданных (S-12-класс).

### 4.5. Режим 18 — атрибуция уточнена (уже исправлено после написания плана)

План: «режим 18 Qwen+FRIDA — ПУСТО, собственный путь, требует разбора». Причина была
в **отсутствующих глобалях** `_QWEN_MODEL`/`_FRIDA_MODEL` в `llm_filter.py` (NameError
мгновенно, 0.0 с) — глобали не вошли в AST-извлечение при миграции, а `global`-декларация
подавляла F821 у ruff. Восстановлены из git HEAD, проверены живым прогоном: **EXACT
с базлайном** (5 результатов, 23.1 с). Подробно — `MAIN_SPLIT_PLAN.md` §6а, §7.

## 7. Дополнительный протокол для всех планов (предложение)

Основываясь на уроках миграции (MAIN_SPLIT_PLAN.md §6а), предлагаю дополнить каждый
план развития следующими правилами:

1. **Measure-first:** любое проектное решение снабжается измерением, выполненным
   **до** написания плана (не «оценка», а факт).
2. **Координаты — по AST, не по строкам:** ссылки на функции — по именам и файлам,
   не по номерам строк (номера устаревают после каждого рефакторинга).
3. **Сканер глобалей с самопроверкой:** проверка «global X в функции, но X не присвоен
   на уровне модуля» — обязательный шаг после любого AST-извлечения. Сканер должен
   иметь самопроверку «ловит заведомую дыру».
4. **Monkeypatch-цели — namespace вызывающего:** при разбиении монолита тесты,
   патчащие `main.X`, обновляются на `astro_app.modes.<module>.X` (namespace
   вызывающей функции, не поставщика).

Все четыре правила уже применены в MAIN_SPLIT_PLAN.md — предлагаю закрепить их
для следующего цикла.
