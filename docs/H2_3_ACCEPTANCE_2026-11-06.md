## 2. Методика: подготовка окружения приёмки

Машина на старт приёмки: Docker отсутствует, WSL2/Hyper-V выключены, Docker Hub недоступен из сети. Всё, что потребовалось, — зафиксировано как воспроизводимая процедура:

1. **WSL2 + Docker Desktop** (один UAC-запрос):
   `wsl --install --no-distribution` → `dism /online /enable-feature Microsoft-Windows-Subsystem-Linux, VirtualMachinePlatform /norestart` → `winget install Docker.DockerDesktop` → **перезагрузка**. Время установки ~2 мин + ребут.
2. **Docker Hub недоступен** (`registry-1.docker.io` → `EOF`). Обход — зеркало Google, затем локальный ретаг под имя из Dockerfile:
   ```
   docker pull mirror.gcr.io/library/python:3.11-slim
   docker tag mirror.gcr.io/library/python:3.11-slim python:3.11-slim
   ```
   После ретага сборка образа идёт полностью локально по кэшу слоёв. Для постоянной настройки — `daemon.json` → `registry-mirrors: ["https://mirror.gcr.io"]` (на момент приёмки хватило ретага).
3. **Проверка сетевого контракта compose до сборки**: LM Studio должна быть видна из контейнера по `host.docker.internal:1234` — проверено одноразовым контейнером (`docker run --rm python:3.11-slim python -c …`): `REACHABLE`, модель `google/gemma-4-e4b` в списке.

## 4. Дефекты, найденные и исправленные в ходе приёмки

### 4.1. Crash-loop: непиненный `transformers` несовместим с `torch 2.5.1` (блокирующий)

**Симптом:** контейнер стартовал (стартовые проверки проходили), затем падал и перезапускался по кругу. В логе:

```
transformers/distributed/pipeline_parallel.py:41 class PipelineIdentityLayer(nn.Identity):
NameError: name 'nn' is not defined
```

**Причина:** `pyproject.toml` задаёт только нижнюю границу `transformers>=4.45.2`; на хосте стояла ровно 4.45.2, поэтому дефект не проявлялся. В чистом контейнере pip взял **последнюю** (5.22.2), модуль `distributed/pipeline_parallel.py` которой требует более новый torch. Старые пины в слое **до** `pip install .` не помогли — резолвер всё равно поднял версию в единой транзакции.

**Исправление (надёжный механизм):** файл `constraints.txt` (transformers 4.45.2, sentence-transformers 5.7.0 — ровно проверенный на хосте/CI стек) + в Dockerfile:

```dockerfile
COPY pyproject.toml README_RU.md .env.example constraints.txt ./
...
RUN python -m pip install . -c constraints.txt
```

После ребилда в образе: transformers 4.45.2 + sentence-transformers 5.7.0, контейнер healthy. Контрактный тест `test_dockerfile_copies_runtime_sources` обновлён (constraints.txt — часть runtime-копии и установка с `-c`).

**Вывод для плана:** любые`>=`-зависимости, критичные к стеку torch, в Docker-пути нужно проводить через constraints — резолвер в чистом окружении гарантированно берёт последние версии.

### 4.2. Дефолт `.env.example` не проходил проверку LM Studio (не блокирующий, UX)

`LLM_NAME=gemma-4-e4b` (имя каталога индекса) без активного `LLM_API_NAME`: start.py подставлял имя без префикса → «модель 'gemma-4-e4b' не найдена» (реальный id в API LM Studio — с префиксом издателя). Исправлено: `LLM_API_NAME=google/gemma-4-e4b` активен по умолчанию; имя каталога индекса осталось в `LLM_NAME`. После фикса «чистый» `.env` проходит проверку модели.

### 4.3. Операционное знание: page-level режим 5 не видит чанки без метаданных (не дефект — контракт)

`_build_page_index` (page_retrieval.py) пропускает чанки без `source_file`/`doc_title` **и** `page_num >= 1`. Следствие: индексация «голым» `HippoRAG.index(docs=[тексты])` невидима для продуктового page-level пути — чанки обязаны нести метаданные страницы (как их делает PDF-пайплайн). Правильный минимальный путь для текстов: `chunk_embedding_store.insert_strings(texts, metadatas=[{source_file, doc_title, page_num, section}, …])`. Именно так собран образцовый индекс приёмки. Рекомендация в docs/ADMIN_GUIDE: ingestion текстов — только с метаданными страниц.

## 5. Конфигурация «модель на другой машине» — подтверждена

Вопрос владельца: можно ли держать модель (`google/gemma-4-e4b`) на другой машине. **Ответ: да, это штатный режим LM Studio (remote-провайдер), и он проверен на всех уровнях:**

* host → `localhost:1234/v1/models` — e4b в списке;
* контейнер → `host.docker.internal:1234` — e4b в списке (сетевой контракт compose работает);
* сквозной заземлённый ответ в контейнере с цитатой — сгенерирован именно e4b (см. §3);
* приёмник `scripts/check_lmstudio.py` и стартовая проверка `start.py` видят remote-модель как обычную.

**Замечание по эксплуатации:** remote-подключение LM Studio **не переживает перезагрузку** — после ребута e4b пропала из списка, а попытка загрузки превращалась в скачивание из Hub (в логе сервера: `POST /api/v1/models/load` → `/models/download`). Remote нужно переподключить в GUI после ребута — после этого конфигурация полностью восстанавливается. Отдельного пина/настройки автоподключения remote в LM Studio 0.4.28 не обнаружено.

## 6. §8.4 Негативные проверки — все подтверждены

| Проверка | Ожидание | Факт |
|---|---|---|
| LM Studio на мёртвом порту (`127.0.0.1:9`) | отказ, код 1, подсказка | ✅ `exit=1`, «Подключение не установлено…» + подсказка |
| Удалить `.env` | создаётся из `.env.example` | ✅ создан (и, после фикса 4.2, дефолт проходит проверку модели) |
| `--host 0.0.0.0` без `API_KEY` | отказ | ✅ `exit=1`, «Для адреса вне loopback нужен API_KEY» |
| Loopback без `API_KEY` | fail-open с предупреждением | ✅ «API_KEY не задан; для loopback включаю API_KEY_REQUIRED=0» → «Проверки пройдены», `exit=0` |

Методическая заметка: код выхода проверялся **без пайплайнов** (`cmd > file; echo $?`) — `$?` после `cmd | tail` возвращает код `tail`, что даёт ложный «успех».

## 7. Оценка критерия «≤ 15 минут» и ограничения

* **Замер на этой машине (не чистой):** клона не требовался (репо уже локально), сборка 178–240 с + healthy ~30–60 с + разовые загрузки (CE-ru ~700 МБ в замере 28,9 с; embedding-модель скачивается один раз при первой индексации). Первый заземлённый ответ — в пределах **≤ 15 мин** с запасом даже с разовыми загрузками при рабочей сети.
* **Оговорка:** машина не «чистая» (pip/HF-кэши, уже настроенный LM Studio). На действительно чистой машине доминирующие слагаемые — клон репо, `docker compose build` (тянуть ~1,5 ГБ wheel'ов) и разовые модели; по замерам этого прогона бюджет 15 минут достижим, но финальная цифра — за приёмкой на чистой VM (нет на этой машине: Docker только что установлен, второй ОС нет).
* **Не выполнялось:** §8.2 Linux (`start.sh`), повторный Docker-прогон на другой машине.
* **H2-4 наблюдаемость** подтверждена попутно живьём: структурные JSON-логи (`ask_completed` со stages/ms), `/metrics`, тайминги стадий в ответе API.
