### 1.1. Корпус: компактная схема «гуа N (… шен-ци …)» есть для всех чисел, кроме 5

### 1.2. У гуа 5 направление в книге есть — в распределённой форме

Ранее здесь стоял вывод «не по схеме Шен-ци, значит направления нет». Он
**опровергнут** справкой автора книг и повторным сканом корпуса:

- чанк 1115, стр. 25: «Мужчина-пятёрка опирается на знания (**северо-восток**),
  а женщина-пятёрка — на сотрудничество (**юго-запад**)».
- Резюме, стр. 99–101: «„ПЯТЁРКАМ“-МУЖЧИНАМ … (центр, **северо-восток**)»,
  «„ПЯТЁРКАМ“-ЖЕНЩИНАМ И „ВОСЬМЁРКАМ“ … (центр, **юго-запад**)».
- чанк 1215, стр. 73: «Число гуа 5 (женщины) и 8. Лучшее направление для
  **образования** и развития личности — **северо-восток**».
- Тематическая сетка: мужчины-«пятёрки» идут в паре с гуа 2 (здоровье запад,
  стр. 55; романтика северо-запад, стр. 62; развитие юго-запад, стр. 70;
  форс-мажор юго-восток, стр. 80; юридические юг, стр. 88; крах север, стр. 96);
  женщины-«пятёрки» — в паре с гуа 8 (здоровье северо-запад, стр. 58; романтика
  запад, стр. 65; образование северо-восток, стр. 73; форс-мажор север, стр. 84;
  юридические восток, стр. 90; крах юго-восток, стр. 96). Стр. 29 и 111
  подтверждают соответствие «северо-восток = шен-ци гуа 2», «юго-запад =
  шен-ци гуа 8».
- Приложение №2 («Поражения по гуа») — другая система координат, к шен-ци не
  относится.

**Вывод (исправлен).** Направление у гуа 5 есть: мужчине-«пятёрке» — северо-восток
(знания, как гуа 2), женщине-«пятёрке» — юго-запад (сотрудничество, как гуа 8);
сами «пятёрки» — центр ЛО-ШУ. Отказ на вопросе владельца — **дефект retrieval**
(лексический разрыв «шен-ци ↔ лучшее направление»), а не корректное поведение.
Вопрос — **answerable**, в unanswerable-секцию golden set его добавлять нельзя.

### 1.4. 500: где рождается и почему её не видно

Цепочка: `POST /api/ask` → `server.py:60-73` → `service.answer_question` → исключение →
`server.py:76-87` → `HTTPException(500, "Внутренняя ошибка поиска")`.

След теряется в трёх местах:

- **A. Файловый журнал не включается никогда.** `configure_file_logging()`
  (`logging_setup.py:61-90`) берёт путь только из `HIPPORAG_LOG_FILE`
  (`logging_setup.py:20`, `_resolve` — `:33-37`); если переменной нет, функция
  возвращает `None` и обработчик не создаётся. Проверено: переменная **не задана ни
  в одном** месте репозитория — ни `scripts/start.py`, ни `.env`/`.env.example`, ни
  `start.bat`/`start.sh`, ни `docker-compose.yml`; единственное упоминание —
  в самом `logging_setup.py`. При этом docstring модуля (`logging_setup.py:4-6`)
  прямо утверждает «`scripts/start.py` выставляет переменную сам» — **это неверно**,
  и именно из-за этого дефект не заметили. Итог: `server.py:57`
  (`_LOG_PATH = configure_file_logging()`) всегда даёт `None`, `logger.exception`
  (`server.py:86`) уходит только в stdout дочернего процесса и исчезает вместе с ним.
- **B. Структурные события не доедут в файл даже после починки A.**
  `observability.py:35` — `_event_logger.propagate = False`, обработчик только
  `StreamHandler` (`observability.py:36-39`). События `ask_failed` / `ask_completed` /
  `answer_empty` с `error_type` и `error` не попадут в root-обработчик файла.
- **C. В ответе HTTP нет причины.** `server.py:76-87` отдаёт обезличенный
  `detail="Внутренняя ошибка поиска"`; имя и текст исключения остаются только в
  stdout-событии, которое по (A) тоже потеряно. Пользователь видит одну и ту же
  строку и при недоступности LLM, и при падении графа, и при переиндексации.

### 1.5. Найденная точка 500 в режиме 1 (много-векторный)

`query.py:176-248` (`reformulate_query`) — режим 1 (`modes/dense.py:12-75`) единственный
из трёх UI-режимов, кто зовёт LLM **до** retrieval:

- `query.py:183` — `httpx.get(f"{api_url}/v1/models", timeout=3)`;
- `query.py:189` — `except (httpx.ConnectError, httpx.TimeoutException)` — **узко**.
  Остальные `httpx.HTTPError` (например `httpx.RemoteProtocolError` при перезапуске
  или перезагрузке LM Studio) сюда не попадают → исклюнение уходит наружу →
  `server.py:76` → 500.
- Второй вызов (`query.py:220`) защищён широким `except Exception` (`query.py:244`).

Режим 5 LLM в retrieval не зовёт вовсе (`modes/bm25_hybrid.py:45-76` — только BM25 +
RU-cross-encoder), поэтому при том же сбое LM Studio он не падает. Это объясняет
асимметрию «режим 5 отказался, режим 1 упал в 500». Для режима 2
(`modes/graph.py:20+`, entity linking + PPR) LLM в retrieval тоже не зовётся — его
кандидат на 500 лежит в графовом пути (`prepare_retrieval_objects`, `run_ppr`,
`dense_passage_retrieval`), и определить его без журнала нельзя.

### 1.6. Что исключено как причина 500 (отрицательные результаты)

- **Рассинхрон индекса** `Length mismatch: passage_node_keys=1369,
  ner_results_dict=1370, triple_results_dict=1370` (`HippoRAG.py:1652-1657`) —
  предупреждение, а не причина: сразу после него код **дочиняет** недостающие ключи
  пустыми `NerRawOutput`/`TripleRawOutput` (`HippoRAG.py:1659-1668`). Аварийно
  индекс не трогаем (см. F-11 — это гигиена, отдельная задача).
- **LLM в UI-пути** — `grounded_qa.py:139-140` ловит `Exception` и возвращает `""`.
  Ответ LLM не может вызвать 500; максимум — честный отказ
  `llm_unavailable_or_empty` (`service.py:341-342`).
- **QA-кэш / llm-кэш** — см. §1.3, в UI-пути не используются.

### 1.7. Отдельно: event loop заморожен на всё время запроса

`server.py:60-73` — `async def ask`, внутри которого **синхронно** выполняется весь
пайплайн (retrieval + LLM). Пока идёт запрос, `/health`, `/metrics` и повторные
клики стоят в очереди: измеренная длительность запроса — в среднем 15,4 с, максимум
25 с (по `/metrics` на момент расследования), а при зависшем LM Studio — до
**300 с** (таймауты: `grounded_qa.py:116`, `query.py:220`, `llm/openai_gpt.py:275`).
Это и есть «залипание» интерфейса, на которое наступил владелец, перетыкая режимы.

### 1.8. Причина отказа пользователю не показывается

UI не читает `grounding_errors` вообще: в `src/astro_app/web/static/app.js` поле не
упоминается (проверено grep'ом), баннер отказа показывает только общий текст. Поэтому
три разные ситуации — «в корпусе нет факта» (корректно), «LLM недоступна» (временный
сбой), «не распарсился ответ» (дефект парсера) — выглядят одинаково.

### P1 — устойчивость и отзывчивость

#### F-4. Не глушить сетевые ошибки в режиме 1  · 0.5 дня
**Суть.** `query.py:189` ловит только `(ConnectError, TimeoutException)`. Заменить на
`except httpx.HTTPError` (покрывает `RemoteProtocolError`, `ReadError`, `PoolTimeout`
и пр.) с тем же поведением: поиск продолжается на исходном запросе. Это убирает
целый класс 500 в режиме 1 при перезапуске LM Studio.
**Приёмка.** Тест: `httpx.get` бросает `httpx.RemoteProtocolError` → `reformulate_query`
возвращает исходный запрос, исключение не выходит; режим 1 отдаёт 200 с отказом или
ответом, а не 500.

#### F-5. Снять блокировку event loop  · 1.5 дня (+ замок)
**Суть.** `server.py:60-73` — пайплайн выполняется в event loop. Перенести в
`run_in_executor` с семафором на 1–2 одновременных запроса.
**Риск, который обязателен к закрытию в этой же задаче.** Сейчас запросы
сериализованы блокировкой; при выносе в потоки общий объект `hipporag` станет
доступен конкурентно: `igraph` (PPR в `HippoRAG.run_ppr`) не потокобезопасен,
ленивая загрузка моделей (`_get_crossencoder_ru`, эмбеддинги) не защищена локами.
**Где.** `server.py` + общий `threading.Lock` вокруг графовых вызовов
(`prepare_retrieval_objects`, `run_ppr`, `dense_passage_retrieval`) и вокруг
ленивой загрузки моделей.
**Приёмка.** Два параллельных `/api/ask` (режимы 2 и 1) завершаются без ошибок;
`/health` отвечает во время выполняющегося запроса (≤ 1 с); `igraph`-часть не падает
при 10 параллельных запросах в режиме 2.

#### F-6. Единый бюджет таймаута LLM  · 0.5 дня
**Суть.** Три независимых «300 с» (`grounded_qa.py:116`, `query.py:220`,
`llm/openai_gpt.py:275`) — слишком долго для UI. Ввести `LLM_TIMEOUT`
(по умолчанию 90 с) и использовать его во всех трёх местах; для UI — отдельный,
более короткий бюджет (60–90 с), для CLI — текущие 300 с.
**Приёмка.** При недоступном LM Studio запрос падает/отказывается не позже
`LLM_TIMEOUT + 5 с`, а не через 300 с; значение берётся из окружения.

#### F-7. Прогрев моделей и графа при старте сервера  · 0.5 дня
**Суть.** Первый запрос после старта попадает в JIT-загрузку cross-encoder,
эмбеддингов и графа — отсюда «первый вопрос hangs, второй быстрый». Прогреть
модели на старте (в фоне, с логом) и отдавать в `/health` признак готовности.
**Приёмка.** Первый `/api/ask` после старта — не дольше типичного (в пределах
p50 + 20 %), `/health` показывает `ready: true` после прогрева.

### P2 — качество ответа и честность метрик

#### F-8. Различать причины отказа в UI  · 0.5 дня
**Суть.** `grounding_errors` (`service.py:338-342`) не доходит до пользователя.
Три разные причины (`no_fragments`, `llm_unavailable_or_empty`, ошибки парсинга
заземления) должны давать разный текст и разный тон: «в книгах нет этого факта» /
«LLM временно недоступна, попробуйте ещё раз» / «ответ не удалось проверить».
**Где.** `web/static/app.js` + `web/static/index.html` (баннер отказа).
**Приёмка.** Для вопроса про гуа 5 в UI видно, что отказ из-за отсутствия факта, а
не из-за сбоя LLM; на `/api/ask` в `grounding_errors` остаётся машинный код причины.

#### F-9. Отказ с пояснением вместо голого «нет ответа»  · 1 день
**Суть.** Для «гуа 5» в корпусе есть смежные факты (чанк 1215 — направление
образования северо-восток; чанк 1115 — мужчина/женщина: знания/сотрудничество).
Система должна отвечать по существу: «собственного направления Шен-ци у числа гуа 5
в книгах нет; мужчина-пятёрка опирается на знания (северо-восток), женщина-пятёрка —
на сотрудничество (юго-запад)» — **с цитатами на эти чанки**. Это честный ответ
с оговоркой, а не отказ.
**Где.** Промпт заземления (`hipporag/prompts/templates/rag_qa_astrology.py`) +
контракт парсера (`hipporag/qa/grounding.py`) — нужно разрешить ответ «факта нет,
но вот что есть», не ломая строгий режим (когда модель не привела ни одной ссылки —
по-прежнему отказ).
**Приёмка.** На вопрос про гуа 5 ответ содержит явное «в корпусе нет … Шен-ци» и
ссылки на реальные страницы; на контрольных вопросах из golden set поведение не
меняется (регрессия ≤ 0 ответов).

#### F-10. Разделить in-tune и out-of-tune вопросы в метриках  · 0.5 дня
**Суть.** «Какое направление Шен-ци у числа гуа 1?» лежит в eval-датасете
(`eval/dataset/questions.jsonl:23`, qid `домен-гуа-1-шен-ци`) и участвовал в выборе
режима/чанкинга/порогов → метрики по нему завышены (эффект подгонки, не утечка).
**Где.** `eval/grounding/golden_qa.jsonl` — ввести поле `split: in_tune|out_of_tune`
и считать метрики раздельно; вопрос про гуа 1 пометить `in_tune`.
**Приёмка.** В отчёте по grounding видны обе метрики; «гуа 5» добавлен в
unanswerable-секцию golden set (факт отсутствует — это корректный отказ, и он
должен считаться успехом, а не провалом).

### P3 — гигиена (не блокирует ручной тест)

#### F-11. Снять рассинхрон индекса  · 0.5 дня
`Length mismatch: passage_node_keys=1369, ner_results_dict=1370, triple_results_dict=1370`
(`HippoRAG.py:1652-1657`) — OpenIE-результат на один чанк больше, чем чанков в
индексе; код дочиняет это на лету. Нужно найти чанк, потерявшийся при
переиндексации, и пересобрать индекс, чтобы предупреждение не появлялось.
**Приёмка.** Индекс грузится без warning; число OpenIE-результатов == числу чанков.

#### F-12. Убрать O(n) поиск метаданных в горячем пути  · 0.5 дня
`service.py:176-184` — `_metadata_for_text` ищет текст через `texts.index(text)`
(линейно по 1369 чанкам на каждый фрагмент). Заменить на предсобранный
`dict[text → index]`, строимый один раз при загрузке индекса.
**Приёмка.** Время `retrieve` для 5 фрагментов не растёт линейно от размера
индекса; поведение (метаданные, цитаты) не меняется — проверяется существующими
тестами `test_p0_2_metadata.py`.

### F-14. Сброс вопроса/ответа при переходе «Статус» и повторный запрос ключа  · 0.5–1 день

**Симптом (ручная проверка владельца, 2026-11-07):** во время ожидания ответа
клик «Статус» → возврат «К поиску» — вопрос и ответ пропали; при открытии
«Статуса» интерфейс повторно запрашивает API-ключ.

**Корневая причина.** «Статус» (`/ui/dashboard`) — отдельная страница: переход
перезагружает вкладку, а состояние поиска (вопрос, последний ответ,
незавершённый запрос) живёт только в памяти JS страницы и погибает. Ключ
хранится в `sessionStorage` — он привязан к вкладке: дашборд, открытый в
новой вкладке, его не видит.

**Отменённая попытка (2026-11-07, коммиты f9e29c5 + 320b86c, откат cec0f6b).**
Было сделано: «Статус» в новой вкладке; ключ/последний ответ перенесены в
localStorage; авто-повтор прерванного запроса. Почему отозвано: владелец
получил «Ключ не подошёл или ещё не введён» на вкладке дашборда — правка
`dashboard.js` (чтение ключа из localStorage) не была завершена и закоммичена,
владелец закрыл исходную вкладку и продолжил в дашборде, где состояния не
было. Урок: менять хранилища надо **сразу на обеих страницах** и проверять в
реальном браузере весь сценарий до передачи владельцу.

**Как исправлять (следующая итерация).**
1. Предпочтительно: дашборд встраивается в страницу поиска (секция/iframe по
   кнопке «Статус») — уход со страницы исчезает как класс проблемы.
2. Если оставлять отдельную страницу: ключ читается и пишется в
   `localStorage` в **обоих** скриптах (`app.js` и `dashboard.js`); последний
   ответ и незавершённый запрос — тоже в `localStorage`, с авто-повтором.
3. Проверка — в реальном браузере, весь сценарий: вопрос → «Статус» → назад →
   вопрос и ответ на месте; ключ не запрашивается повторно; незавершённый
   запрос доезжает. Юнит-тесты JS-логики не заменяют эту проверку.
4. Известный косметический попутно: служебные фрагменты (таблица гуа,
   уточнение автора) в списке источников показывают «стр. — » — подписать
   «вне издания».

**Приёмка.** Сценарий выше воспроизведён владельцем без замечаний; ни одна
из серверных метрик не меняется (правки только статики).

## 5. Чего делать не надо

- **Не дописывать «гуа 5 → направление Шен-ци» в корпус, промпт или словарь.**
  Факта в книгах нет; «дорисовка» — это подгонка под тест и подрыв доверия к
  цитатам. Правильный ответ — честный отказ с пояснением (F-9), а не выдумка.
- **Не «чинить» отказ по гуа 5 в retrieval.** Он корректен: покрытие корпуса
  асимметрично, а система обязана это показывать.
- **Не переиндексировать в попытке вылечить 500.** Индекс не при чём: причина
  потери следа — наблюдаемость, а рассинхрон (F-11) код дочиняет сам.
- **Не перезаписывать `origin` и не создавать PR в upstream.** Ветка личная,
  upstream не участвует.
- **Не менять `hipporag` как пакет** (переименование, версии) в рамках этих задач —
  это отдельная история из `docs/DEVELOPMENT_PLAN_MAVIS_2026-11-02.md`.
