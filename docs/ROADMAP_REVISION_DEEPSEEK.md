## 1. Резюме

### 1.1. Одна страница

`L-MORIA/HippoRAG` — это **не форк upstream, а самостоятельный продукт** на его основе:
русскоязычная RAG-система по астрологии и астрофэншуй с 23 режимами поиска, графом знаний,
локальными LLM через LM Studio и работой полностью на CPU.

Проект **сильнее, чем типичный личный RAG-форк**. В нём есть настоящий аудит (45 находок),
96 unit-тестов, baseline-снапшоты, реестр режимов, CI, QA-кэш с версионностью и честная
документация о границах решений. Разделение `main.py` на 20 модулей выполнено аккуратно,
с проверкой эквивалентности по 23 режимам.

Но у проекта есть **три факта, которые важнее всего содержимого `ROADMAP.md`**:

1. **Чистый клон не запускается.** `astro_app/data/synonyms.json` отсутствует в git:
   правило `.gitignore:20 data/` игнорирует пакетные данные. В рабочем дереве файл есть,
   поэтому локально всё работает; в чистом клоне — `ModuleNotFoundError: No module named
   'astro_app.data'`.
2. **CI красный на всех прогонах после split.** Последний завершённый прогон
   `41506642873`: **40 failed, 63 passed, 7 errors**. При этом
   `docs/COMPLETION_REPORT_2026-11-02.md` утверждает «CI-ворота зелёные».
3. **Выбор модели в меню не доходит до большинства режимов.** Семь модулей импортируют
   `LLM_NAME` по значению, а `cli.py` меняет `config.LLM_NAME`. В результате
   `HippoRAG` использует новую модель, а прямые HTTP-вызовы в режимах 1, 7, 12, 18, 19,
   21, 22 — старую; QA-кэш при этом штампуется новой моделью.

Из этого следует главный вывод ревизии:

> **`ROADMAP.md` — это качественный план ремонта, а не план развития.**
> Он хорошо чинит уже найденные дефекты, но не замечает, что поставляемый артефакт
> неработоспособен, и не отвечает на вопрос, каким продуктом проект должен стать.

### 1.3. Что делать в первую очередь

Не писать ещё один аудит и не добавлять 24-й режим. Сделать **H0 за 1–2 дня**:

1. вынести `synonyms.json` из игнорируемого `data/`;
2. починить `LLM_NAME` в семи модулях;
3. убрать дубль `__all__`;
4. привести docs к коду;
5. переименовать distribution и выключить публикацию в чужой PyPI-пакет;
6. сделать CI дешёвым и зелёным;
7. выровнять ветки и поставить тег.

После этого — **H1**: eval-база, роутер, топ-3 режима, performance-бюджет, ablation графа.
И только потом — продуктовая оболочка и масштабирование.

## 2. Что за проект

### 2.1. Продукт

**Astrology RAG** — локальная русскоязычная система поиска по книгам по астрофэншуй.
Корпус — три PDF:

1. астрофэншуй;
2. психологический фэншуй;
3. эзотерический фэншуй.

Система отвечает на вопросы двух типов:

- **фактологические** — «какие книги написала Максимова И.В.?», «что такое Багуа?»,
  «какое число гуа у человека, рождённого в 1985 году?»;
- **доменные** — «какая зона подходит для Овна?», «где в квартире расположить плиту?»,
  «что означает сектор богатства?».

Ответ сопровождается цитатами: `source_file`, `doc_title`, `page_num`, `section`,
`text_snippet`. Это принципиально: система не «сочиняет», а показывает, откуда взяла
фрагмент.

### 2.2. Архитектура

Условно проект делится на четыре слоя:

```
┌─────────────────────────────────────────────────────────────────────┐
│ 1. Вход                                                             │
│    main.py (фасад) → astro_app/cli.py → меню 23 режимов             │
│    hipporag.bat, menu.py, test_menu.bat                             │
├─────────────────────────────────────────────────────────────────────┤
│ 2. Прикладной слой astro_app                                        │
│    config, query, primitives, rerankers, qa_cache, display,         │
│    synonyms, signs, textutils, modes/* (11 модулей, 23 режима)      │
├─────────────────────────────────────────────────────────────────────┤
│ 3. Ядро HippoRAG (upstream + локальные доработки)                   │
│    HippoRAG.py, OpenIE, граф, PPR, embedding stores, PDF ingestion, │
│    FastAPI (/search, /ingest, /health)                              │
├─────────────────────────────────────────────────────────────────────┤
│ 4. Внешние зависимости                                             │
│    LM Studio (4 локальные LLM), sentence-transformers,              │
│    cross-encoder RU/EN, ColBERT, BM25, igraph, Tesseract OCR        │
└─────────────────────────────────────────────────────────────────────┘
```

Ключевое архитектурное решение — **реестр `MODES`** в
`src/astro_app/modes/__init__.py`. Это единственный источник истины для меню,
диспетчера и `_qa_run_test`: добавление режима — одна запись, а не правка в четырёх
местах. Контракт вызова `fn(hipporag, query)` сохраняет дефолты каждого режима.

## 4. Сильные стороны

Этот раздел важен не для вежливости. Он фиксирует, что **не надо переделывать**,
и объясняет, почему проект заслуживает аккуратного отношения.

### 4.1. Аудит действительно глубокий

45 находок S-01…S-45 — это не список «поправьте опечатки». У каждой есть корневая
причина, а не симптом. Три примера, которые показывают уровень:

- **P0-2.** `_get_chunk_meta` не понимал список метаданных. Симптом — «8 режимов
  возвращают пустоту». Корень — смена формата метаданных при переиндексации (фикс S-12),
  которую приёмка не поймала, потому что проверяла целостность индекса, а не методы
  поиска.
- **P1-4.** Сырой CE-скор (логит/вероятность/cosine) смешивался с embedding-скором.
  Корреляция CE с релевантностью была **−0,189**, стала **+0,336** после нормировки.
  Это редкий случай, когда в личном проекте измеряют не только «стало ли меньше
  падений», но и «стало ли правильнее».
- **P1-10.** GraphRAG Agent вообще не имел `return`. Найден не чтением, а полным
  прогоном всех 23 режимов. Это правильная методика: интеграционный прогон ловит то,
  чего не видит unit-тест.

### 4.2. Разделение `main.py` выполнено образцово

- Было **4 070 строк** в одном файле; стало — фасад **220 строк** + `astro_app`
  (~3 900 строк в 20 модулях).
- Каждый шаг — отдельный коммит с проверкой:
  - шаг 1: `synonyms.json` в пакете, wheel содержит данные, `load_synonyms()` ==
    `main.SYNONYM_MAP` (66 ключей);
  - шаг 2: эквивалентность stdout на реальных данных всех 23 режимов;
  - шаг 3: реальный QA-кэш (6 записей) + запись/экспорт во временных копиях;
  - шаг 4: BM25 1 369 скоров идентичны, `_get_chunk_meta` 50/50;
  - шаг 5: CE-en/ru идентичны, ColBERT bit-exact (`max_diff=0`);
  - шаг 6: 23 режима в 10 модулях, пост-снапшот **21/23 EXACT**;
  - шаг 7: реестр `MODES`, диспетчер без `if/elif`, тесты на namespace вызывающего.
- Это уровень, которого нет у большинства личных проектов: **рефакторинг с
  доказательством эквивалентности**, а не «переписал и надеюсь».

### 4.3. Честная методология

- Есть baseline-снапшоты «до/после» (`outputs/refactor_baseline/pre/`, 23/23 ok,
  manifest с git-HEAD).
- Есть приёмка по критериям, а не по ощущениям.
- Есть раздел «Честно о границах этого решения» — например, признание, что
  `core.hooksPath` всё равно требует локального шага и автоустановки хука не будет.
- Есть признание ложных срабатываний чекера и того, что часть замечаний —
  стилистический долг, а не дефекты.

### 4.4. Доменная адаптация

- Русский NER и извлечение фактов.
- Семантический чанкинг с сохранением метаданных (файл, заголовок, страница, раздел).
- Словарь синонимов (66 ключей) и раскрытие запроса.
- Падежные формы знаков и зон («плиту», «кладовку», «спальню»).
- Pattern search «ЗНАК — ЗОНА» за 0,3 с без LLM.
- Цитаты с `page_num` — можно проверить ответ по книге.
- OCR для сканированных PDF, автоматическое определение текстовый/сканированный.

### 4.5. Инфраструктура

- `pre-commit` с black/isort/ruff и базовыми проверками.
- 96 unit-тестов, `pytest` с маркерами `unit`/`integration`/`slow`/`requires_api`.
- CI на GitHub Actions.
- `scripts/verify_all_mavis.py` — 6 критериев приёмки индекса.
- QA-кэш с версией формата (`QA_CACHE_VERSION = 2`), чтобы старые записи не
  отдавались как «правильный ответ».
- FastAPI с `/health`, `/search`, `/ingest`; CORS ограничен localhost; опциональный
  `X-API-Key`.
- PDF ingestion с OCR и возобновляемой индексацией.

### 4.6. Продуктовая мысль

Даже в сыром виде видно, что это **не демо**:

- 4 модели на выбор, а не одна захардкоженная;
- QA-кэш и экспорт в JSONL для fine-tuning;
- режим «тестировать все методы и сравнить с кэшем»;
- LLM-free fallback для режимов 21/22;
- честный отказ для специализированных режимов вместо пустого ответа.

### 5.3. P0-C. Выбор модели не влияет на большинство режимов

#### Симптом

Пользователь выбирает в меню, например, `qwen3.6-35b-a3b-claude-4.7-opus-reasoning-distilled@iq4_xs`.
`HippoRAG` (граф, QA) использует её. Но режимы 1, 7, 12, 18, 19, 21, 22 продолжают
ходить в **предыдущую** модель — ту, что была в `config.LLM_NAME` на момент импорта.

#### Доказательства

`src/astro_app/cli.py:66-75`:

```python
cur = " ← текущая" if v[0] == config.LLM_NAME else ""
...
chosen_model = MODEL_OPTIONS.get(model_choice, (None, None))[0] or config.LLM_NAME
if chosen_model != config.LLM_NAME:
    ...
# Динамически: qa_cache штампует записи текущей моделью (как main.LLM_NAME раньше)
config.LLM_NAME = chosen_model
```

Но семь модулей импортируют имя **по значению**:

| Модуль | Строка импорта | Где используется |
|---|---|---|
| `src/astro_app/query.py` | 13: `from .config import LLM_BASE_URL, LLM_NAME, STOP_WORDS` | 198 |
| `src/astro_app/modes/graph.py` | 7: `from ..config import LLM_BASE_URL, LLM_NAME` | 153, 201 |
| `src/astro_app/modes/hyde.py` | 5: `from ..config import LLM_BASE_URL, LLM_NAME` | 32 |
| `src/astro_app/modes/llm_filter.py` | 5: `from ..config import LLM_BASE_URL, LLM_NAME` | 66 |
| `src/astro_app/modes/self_rag.py` | 5: `from ..config import LLM_BASE_URL, LLM_NAME` | 100 |
| `src/astro_app/modes/sentence_dat.py` | 8: `from ..config import LLM_BASE_URL, LLM_NAME` | 114, 229, 263, 271 |
| `src/astro_app/modes/sign_zones.py` | 5: `from ..config import LLM_BASE_URL, LLM_NAME` | 185, 342 |

Механика Python:

```python
# config.py
LLM_NAME = "gemma-4-e4b"

# graph.py
from ..config import LLM_NAME   # ← создаёт локальную ссылку на строку
# ...
"model": LLM_NAME               # ← всегда "gemma-4-e4b", даже если config.LLM_NAME изменён
```

`config.LLM_NAME = chosen_model` меняет атрибут модуля `config`, но **не**
локальные переменные, уже импортированные в другие модули. Строки неизменяемы,
поэтому это не «ссылка на переменную», а копия значения.

#### Влияние

1. **Разные модели в одном ответе.** Графовая часть — новая модель, прямой
   HTTP-вызов в режиме — старая. Пользователь видит несогласованный ответ.
2. **Отравление QA-кэша.** `qa_cache.py:120` штампует запись
   `"model": config.LLM_NAME` (новая модель), хотя ответ сгенерировала старая.
   При следующем запросе кэш сочтёт запись актуальной и отдаст её.
3. **Невоспроизводимость.** Замеры «на модели X» могут быть фактически сделаны
   на смеси X и Y.
4. **Стоимость.** Пользователь выбирает «лёгкую и быструю» Nemotron, а получает
   таймауты 300 с от Gemma — и не понимает почему.

#### Исправление

В каждом из семи модулей:

```python
# было
from ..config import LLM_BASE_URL, LLM_NAME
...
"model": LLM_NAME,

# стало
from .. import config
...
"model": config.LLM_NAME,
```

`LLM_BASE_URL` тоже лучше читать через `config`, если планируется его менять
в рантайме (сейчас — нет, но симметрия полезна).

Тест:

```python
def test_model_selection_propagates(monkeypatch):
    from astro_app import config
    monkeypatch.setattr(config, "LLM_NAME", "test-model")
    payload = build_payload(...)   # или перехват httpx
    assert payload["model"] == "test-model"
```

Лучше — перехватывать `httpx.post` и проверять `json["model"]` для каждого
из семи модулей. Это дешёвый тест, который ловит регрессию навсегда.

#### Приёмка

- Выбор модели в меню меняет `model` во **всех** HTTP-запросах;
- QA-кэш не отдаёт запись, сделанную другой моделью;
- тест на семь модулей проходит.

#### Оценка

1–2 часа.

| 6.5 | **Данные не воспроизводимы** | `data/` и `outputs/` в `.gitignore`; нет PDF, sample-индекса, `HOW_TO_RUN.md` | Новый человек не запустит продукт; вы сами через месяц не восстановите индекс |
| 6.6 | **CI дорогой и устаревший** | 9 test-jobs, v3-actions, security с `\|\| true` | На private-репо ~2000 минут/мес; 9 × 15–20 мин ≈ 2–3 часа на пуш |
| 6.7 | **Ветка `develop` мертва** | `main` +81 / −2 | CI триггерится на неиспользуемую ветку; путаница |
| 6.8 | **Идентичность пакета** | `hipporag`, версия 2.0.0-alpha.4, URL на OSU | См. §5.5 |

### 6.2. Пояснения

#### 6.2.1. Нет боевой оценки качества

`P1-2` в роадмапе честно признаёт: «6 критериев приёмки проверяют целостность
индекса, но не качество ответа». Замер 2026-11-02 — это **smoke**, а не eval:

- 8 запросов;
- релевантность по вхождению подстроки («максимов») в чанк;
- нет ground truth по страницам;
- нет recall@k, MRR, nDCG;
- нет answer correctness;
- нет статистической значимости.

Этого достаточно, чтобы найти «пустые режимы» и грубые провалы. Недостаточно,
чтобы ответить: «стало ли лучше после 45 фиксов?», «какой режим лучший?»,
«ухудшился ли граф после переиндексации?».

#### 6.2.2. 23 режима — лаборатория, а не продукт

После исправлений 11 режимов дают 8/8. Остальные 12 делятся на:

- **специализированные** — 9/10/11 (нужен знак), 22/23 (нужна зона), 20
  (ищет предложения) — для них нужен честный отказ или пояснение в меню;
- **недобирающие** — 12 (BM25 вместо dense), 21 (отказ LLM), 19/14/18 (частично).

Продукт не может предлагать пользователю 23 кнопки без объяснения. Нужен
**роутер**: система сама определяет тип запроса и выбирает 1–3 режима.
Остальные 20 — в «экспертный» раздел.

#### 6.2.3. Нет бюджета latency

| Режим | Время | Комментарий |
|---|---|---|
| 18 Qwen+FRIDA | **97,3 с** | самый долгий |
| 21 DAT+LLM | **41,9 с** | |
| 19 GraphRAG | **29,7 с** | |
| 12 Self-RAG | **22,1 с** | |
| 7 HyDE | **20,5 с** | |
| 17 LLM-фильтр | **10,3 с** | |
| 20 Sentence-level | **9,9 с** | |
| 2 Граф | **1,0 с** | лучший по скорости/качеству |
| 5 BM25+CE-ru | **2,4 с** | |
| Загрузка индекса | **7,4 с** | |
| Полный прогон 23 режимов | **≈4,5 мин** | машинное время |

Для интерактивного поиска 97 с — это отказ пользователя. Нужны:

- p95 default ≤ 10 с;
- LLM-режимы ≤ 30 с;
- всё, что > 30 с — помечено «экспериментальный» и выключено по умолчанию;
- кэш эмбеддингов, ответов, query expansion;
- параллельные вызовы.

#### 6.2.4. Граф перекошен в synonymy

736 089 рёбер, из них 726 250 — synonymy. Это **98,7 %**. PPR по такому графу
может «размываться»: масса случайных связей между похожими сущностями
конкурирует с реальными фактами.

Нужен ablation:

- с synonymy / без synonymy;
- `synonymy_edge_topk` и порог 0,8;
- влияние на recall@10 и latency.

Возможно, окажется, что synonymy помогает recall, но вредит точности. Сейчас
это не измерено.

#### 6.2.5. Данные не воспроизводимы

- PDF лежат в `data/`, который в `.gitignore`.
- `outputs/` в `.gitignore`.
- Нет sample-индекса (хотя бы 100 чанков) для CI и нового разработчика.
- Нет `HOW_TO_RUN.md`.
- Нет manifest индекса: версия, модель, дата, хеши PDF.

Следствие: **индекс нельзя восстановить из репозитория**. Через месяц вы не
вспомните, какой моделью и на каких PDF он построен.

#### 6.2.6. CI дорогой и устаревший

- 9 test-jobs: 3 OS × 3 Python. Для проекта, который реально работает на
  Windows + LM Studio, macOS-джобы почти бесполезны.
- `actions/upload-artifact@v3` и `download-artifact@v3` — GitHub вывел v3 из
  обращения; job упадёт на upload, даже если тесты пройдут.
- `codecov/codecov-action@v3` — устарел.
- `actions/setup-python@v4` — работает, но v5 актуален.
- `security` job: `bandit ... || true`, `safety check ... || true` — **всегда
  зелёный**, то есть не ворота, а декорация.
- Нет `timeout-minutes`, нет `concurrency`, нет `paths-ignore` для docs.
- `lint` гоняется в 3 копиях (3 Python), хотя результат одинаковый.

На private-репо минуты из пула Free (~2 000/мес). Один пуш = 2–3 часа машинного
времени. Несколько пушей в день — и лимит исчерпан.

#### 6.2.7. Ветка `develop` мертва

`main` впереди `origin/develop` на **81 коммит** и отстаёт на **2**. CI при этом
триггерится на `develop`. Это создаёт:

- ложное ощущение «две ветки»;
- лишние прогоны;
- риск смерджить устаревшее.

Решение: либо удалить `develop`, либо сделать её актуальной и ввести правило
«фича → PR в develop → main». Сейчас — удалить.

#### 6.2.8. Идентичность пакета

См. §5.5. Добавлю только: `README.md` — upstream-ный, и `pyproject.toml`
указывает `readme = "README.md"`. То есть **даже если** опубликовать пакет,
страница PyPI будет описывать HippoRAG 2 от OSU, а не ваш продукт.

#### 6.2.9. Нет наблюдаемости

`/health` отдаёт `status`, `version`, `uptime`, `chunks`, `facts`. Этого мало:

- нет per-stage timings (retrieval / rerank / LLM);
- нет счётчиков ошибок и таймаутов;
- нет версии индекса и модели в ответе;
- нет трассировки запроса (какой режим, какие кандидаты, какой prompt).

Без этого нельзя ответить на вопрос «почему этот запрос занял 97 секунд» и
«почему ответ не содержит источник».

#### 6.2.10. Нет жизненного цикла данных

- Добавление книги — `add_documents.py` / `index_pdfs.py`.
- Удаление — `delete_document.py`.
- Переиндексация — `reindex_with_base.py` / `reindex_with_multilingual.py`.
- Версии индекса нет.
- Manifest нет.
- Backup/restore — вручную.

Для продукта нужен сценарий: «загрузил PDF → индекс обновился → старый индекс
сохранён → можно откатиться».

## 7. Постатейный разбор `ROADMAP.md`

### 7.1. Что это за документ

`docs/ROADMAP.md` — 63 КБ, 713 строк. Структура:

- P0 — процесс и работоспособность (P0-1, P0-2, P0-3);
- P1 — качество продукта (P1-1…P1-10);
- P2 — сопровождаемость (P2-1…P2-9);
- порядок работ на 3 недели;
- приложения: замеры 23 режимов, контрольный прогон, «что осталось за рамками»,
  перевод в private.

Формат каждой задачи:

- **Проблема/Состояние** — симптом и корень;
- **Что сделать** — шаги;
- **Приёмка** — проверяемый критерий;
- **Оценка** — время;
- иногда **Риск** и **Честно о границах**.

Это хороший формат. Проблема не в форме, а в приоритетах и охвате.

### 7.2. Что в нём сильно

1. **Диагностика, а не список хотелок.** Каждая задача начинается с факта,
   а не с «надо бы».
2. **Правильно найдены главные дефекты:** P0-2 (`_get_chunk_meta`), P1-4
   (нормировка CE), P1-5 (мета-ответы LLM), P1-6 (Self-RAG), P1-7
   (библиографические вопросы), P1-8 (знак в SemFilter/QACache), P1-9
   (версионность кэша), P1-10 (GraphRAG без `return`).
3. **Разделение `main.py`** описано образцово: baseline-снапшот, 7 шагов,
   проверка эквивалентности, откат.
4. **Честность.** Есть раздел «Что осталось за рамками плана», признание, что
   приёмка проверяла не тот слой, и «Честно о границах» для P0-1.
5. **Приложения с замерами.** Таблица 23 режимов, контрольный прогон, Run A/Run B —
   это редкая для личных проектов доказательная база.
6. **Оценки реалистичны для ремонта.** 30 мин на Self-RAG, 1 ч на промпты,
   0,5–1 день на vector store — это адекватно.

### 7.3. Что в нём слабо

#### 7.3.1. Приоритеты перепутаны

| Задача | Приоритет в роадмапе | Как должно быть |
|---|---|---|
| P0-1 (хук в репозитории) | **P0** | P2 — процессная мелочь, не блокирует продукт |
| Красный CI | **отсутствует** | **P0** |
| Нерабочий чистый клон | **отсутствует** | **P0** |
| `LLM_NAME` | **отсутствует** | **P0** |
| Дубль `__all__` | **отсутствует** | P1 (ломает `import *`) |
| Идентичность пакета | **отсутствует** | **P0** (риск публикации в чужой пакет) |
| P1-2 (оценка качества) | **неделя 2** | **первая задача цикла** |

P0-1 — это 30–40 минут и полезная гигиена, но она не делает продукт
работоспособным. Настоящий P0 — то, без чего `git clone` не запускается.

#### 7.3.2. Нет продуктовой цели

План отвечает на вопрос «что починить», но не на вопросы:

- **Кто пользователь?** Вы сами? Астролог? Студент? Разработчик?
- **Какой сценарий?** «Задал вопрос — получил ответ с цитатой»? «Загрузил книгу —
  нашёл все упоминания»? «Сравнил две книги»?
- **Что считается успехом?** Точность? Скорость? Отсутствие пустых ответов?
- **Когда release?** Что должно быть готово, чтобы назвать версию 1.0?

Без этого невозможно приоритизировать: любая задача выглядит одинаково важной.

#### 7.3.3. Оценка качества до сих пор не сделана

P1-2 стоит на второй неделе, хотя это **главный пункт цикла**. Более того,
оценка «1–1,5 дня» оптимистична:

- 20–30 вопросов с ground truth по страницам — это 1–2 дня только на разметку;
- скрипт eval — 1 день;
- прогон «до/после» — 0,5 дня;
- анализ и таблица — 0,5 дня.

Реально — **3–5 дней**. Лучше запланировать честно.

#### 7.3.4. Нет плана упаковки

- CLI + LM Studio + 4 захардкоженные модели + `.bat`.
- Нет Docker.
- Нет установщика.
- Нет web UI.
- Нет `.env.example`.
- Нет проверки подключения к LM Studio при старте (есть таймауты 300 с вместо
  понятной ошибки).
- Нет `[project.scripts]`.

Продукт, который ставится только «клонируй и запусти из папки», не масштабируется
даже на второго пользователя.

#### 7.3.5. Нет жизненного цикла данных

См. §6.2.10. В роадмапе нет ни одной задачи про:

- версионирование индекса;
- manifest;
- backup/restore;
- incremental indexing;
- add/delete из UI/API;
- миграцию индекса при смене модели эмбеддингов.

#### 7.3.6. Нет performance-бюджета

97-секундный режим 18 не помечен как экспериментальный. Нет p95-лимитов.
Нет задачи «профилировать и ускорить». При этом latency — главный враг
интерактивного поиска.

#### 7.3.7. Нет ablation графа

98,7 % рёбер — synonymy. Не измерено, помогает ли это PPR или вредит. Это
дорогая, но важная задача: возможно, половину рёбер можно убрать и получить
то же качество при меньшей latency.

#### 7.3.8. Документ — это лог, а не план

63 КБ роадмапа + ~300 КБ аудитов. Как audit trail — отлично. Как рабочий
план — тяжело: чтобы понять «что делать сегодня», нужно прочитать несколько
документов и свести их вручную.

Нужен **короткий** `ROADMAP.md` (1–2 страницы) + приложения. Или отдельный
`docs/PLAN_NEXT.md` на 1 страницу.

### 10.2. Как не обмануть себя

1. **Ground truth — из корпуса, а не из памяти.** Эталон должен быть проверен
   по PDF, иначе eval измеряет вашу уверенность, а не качество.
2. **Релевантность — по страницам, а не по подстроке.** Подстрочный критерий
   («чанк содержит „максимов“») завышает recall.
3. **Считать всю выдачу, а не top-1.** Top-1 красив, но пользователь смотрит
   список.
4. **Фиксировать индекс и модель.** Eval на разных индексах несравним.
5. **Разделять retrieval и generation.** Если ответ неверный, сначала проверьте,
   попал ли нужный чанк в top-k.
6. **Считать пустые ответы отдельно.** «Честный отказ» и «пустота» — разные вещи.
7. **Не сравнивать «до/после» на разных вопросах.** Один и тот же набор.

## 14. Вывод

Проект **сильнее, чем типичный личный RAG-форк**:

- есть настоящий аудит с корневыми причинами;
- есть тесты, снапшоты, регрессионные прогоны;
- есть доменная адаптация, которая реально работает;
- есть честная документация о границах решений;
- разделение `main.py` выполнено на уровне, которому можно учить.

Но текущий `ROADMAP.md` — это **план ремонта**, а не **план развития**. Он хорошо
чинит уже найденные дефекты, но:

1. **не замечает, что чистый клон не запускается, а CI красный;**
2. **ставит оценку качества (P1-2) после косметики;**
3. **не решает главную продуктовую проблему — 23 режима вместо одного понятного
   сценария;**
4. **не описывает упаковку, данные и эксплуатацию.**

Правильный следующий шаг — не писать ещё один аудит, а сделать **H0 за 1–2 дня**:

- зелёный чистый клон;
- зелёный CI;
- исправленный выбор модели;
- актуальные docs;
- корректная идентичность пакета.

После этого — **H1**:

- eval-база на 30–50 вопросах;
- роутер и топ-3 режима;
- performance-бюджет;
- ablation графа.

И только потом — **H2/H3**: продуктовая оболочка, жизненный цикл данных,
масштабирование.

### 14.1. Три предложения, если запомнить только их

1. **Сначала сделайте так, чтобы проект запускался у кого-то ещё.** Пока
   `git clone` не работает, всё остальное — самообман.
2. **Сначала измерьте качество, потом улучшайте.** Без eval вы не отличите
   улучшение от перестановки багов.
3. **Один хороший режим лучше 23 неизвестных.** Роутер и топ-3 дадут продукту
   больше, чем 24-й режим.
