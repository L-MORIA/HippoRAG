### 1.1. Одна страница

`L-MORIA/HippoRAG` — это **не форк upstream, а самостоятельный продукт** на его основе:
русскоязычная RAG-система по астрологии и астрофэншуй с 23 режимами поиска, графом знаний,
локальными LLM через LM Studio и работой полностью на CPU.

Проект **сильнее, чем типичный личный RAG-форк**. В нём есть настоящий аудит (45 находок),

## 2. Что за проект

### 2.1. Продукт

**Astrology RAG** — локальная русскоязычная система поиска по книгам по астрофэншуй.
Корпус — три PDF:

1. астрофэншуй;
2. психологический фэншуй;
3. эзотерический фэншуй.

Система отвечает на вопросы двух типов:

- **фактологические** — «какие книги написала Максимова И.В.?», «что такое Багуа?»,
  «какое число гуа у человека, рождённого в 1985 году?»;
- **доменные** — «какая зона подходит для Овна?», «где в квартире расположить плиту?»,
  «что означает сектор богатства?».

Ответ сопровождается цитатами: `source_file`, `doc_title`, `page_num`, `section`,
`text_snippet`. Это принципиально: система не «сочиняет», а показывает, откуда взяла
фрагмент.

### 2.2. Архитектура

Условно проект делится на четыре слоя:

```
┌─────────────────────────────────────────────────────────────────────┐
│ 1. Вход                                                             │
│    main.py (фасад) → astro_app/cli.py → меню 23 режимов             │
│    hipporag.bat, menu.py, test_menu.bat                             │
├─────────────────────────────────────────────────────────────────────┤
│ 2. Прикладной слой astro_app                                        │
│    config, query, primitives, rerankers, qa_cache, display,         │
│    synonyms, signs, textutils, modes/* (11 модулей, 23 режима)      │
├─────────────────────────────────────────────────────────────────────┤
│ 3. Ядро HippoRAG (upstream + локальные доработки)                   │
│    HippoRAG.py, OpenIE, граф, PPR, embedding stores, PDF ingestion, │
│    FastAPI (/search, /ingest, /health)                              │
├─────────────────────────────────────────────────────────────────────┤
│ 4. Внешние зависимости                                             │
│    LM Studio (4 локальные LLM), sentence-transformers,              │
│    cross-encoder RU/EN, ColBERT, BM25, igraph, Tesseract OCR        │
└─────────────────────────────────────────────────────────────────────┘
```

Ключевое архитектурное решение — **реестр `MODES`** в
`src/astro_app/modes/__init__.py`. Это единственный источник истины для меню,
диспетчера и `_qa_run_test`: добавление режима — одна запись, а не правка в четырёх
местах. Контракт вызова `fn(hipporag, query)` сохраняет дефолты каждого режима.

## 4. Сильные стороны

Этот раздел важен не для вежливости. Он фиксирует, что **не надо переделывать**,
и объясняет, почему проект заслуживает аккуратного отношения.

### 4.1. Аудит действительно глубокий

45 находок S-01…S-45 — это не список «поправьте опечатки». У каждой есть корневая
причина, а не симптом. Три примера, которые показывают уровень:

- **P0-2.** `_get_chunk_meta` не понимал список метаданных. Симптом — «8 режимов
  возвращают пустоту». Корень — смена формата метаданных при переиндексации (фикс S-12),

  поиска.
- **P1-4.** Сырой CE-скор (логит/вероятность/cosine) смешивался с embedding-скором.
  Корреляция CE с релевантностью была **−0,189**, стала **+0,336** после нормировки.
  Это редкий случай, когда в личном проекте измеряют не только «стало ли меньше
  падений», но и «стало ли правильнее».
- **P1-10.** GraphRAG Agent вообще не имел `return`. Найден не чтением, а полным
  прогоном всех 23 режимов. Это правильная методика: интеграционный прогон ловит то,
  чего не видит unit-тест.

### 4.2. Разделение `main.py` выполнено образцово

- Было **4 070 строк** в одном файле; стало — фасад **220 строк** + `astro_app`

### 5.5. P0-E. Идентичность пакета и publish-мина

> **Статус v1.2 (возражение Mavis №1): задача разделена на две.**
> **P0-E1** — publish-мина: job настроен на любой тег и использует
> `secrets.PYPI_API_TOKEN`. Сейчас он недостижим из-за branches-only триггера
> (см. ниже), но это P0-конфигурация: достаточно добавить `tags:` — и мина
> активна. Закрывается удалением job за 10 минут.
> **P0-E2** — идентичность пакета: `name = "hipporag"`, `readme = "README.md"`,
> URL на OSU, нет `[project.scripts]`. Это P1/P2: влияет на продукт, но не
> создаёт немедленного риска. Переименование distribution **не закрывает**
> publish-мину и ломает существующую editable-установку.

#### P0-E1. Publish-job: латентная мина — P0

**Симптом.** В `.github/workflows/ci-cd.yml`:

```yaml
publish:
  name: Publish to PyPI
  needs: [build, test]
  if: github.event_name == 'push' && startsWith(github.ref, 'refs/tags')
  steps:
    - uses: pypa/gh-action-pypi-publish@release/v1
      with:
        password: ${{ secrets.PYPI_API_TOKEN }}
```

**Почему это P0, хотя сейчас job не стреляет.** Официальная семантика GitHub
Actions: «If you define only `tags`/`tags-ignore` or only `branches`/
`branches-ignore`, the workflow won't run for events affecting the undefined
Git ref». В workflow задан только `on.push.branches: [main, develop]`, `tags`
нет — значит, push тега **не запускает workflow вообще**, и job `publish` в
текущей конфигурации недостижим. Это не отменяет проблему:

1. job и ссылка на секрет остаются в репозитории как готовая мина: первое же
   добавление `tags:` (типичный шаг при настройке релизов) делает публикацию
   активной;
2. условие `startsWith(github.ref, 'refs/tags')` не ограничивает, **какой
   именно** тег публикуется, — подойдёт любой, включая случайный `v0.2.0`;
3. `needs: [build, test]` — случайная защита, а не осознанная: как только
   тесты станут зелёными, ограничение исчезнет;
4. область действия `PYPI_API_TOKEN` неизвестна, а сам токен хранится в
   настройках репозитория.

Поэтому job удаляется, а не «оставляется, пока не стреляет». Переименование
distribution не меняет триггер и не закрывает мину: job всё равно оживёт на
тег. Поэтому сначала отключается публикация, и только потом обсуждается имя.

**Исправление.**

- Удалить `publish` job **или** заменить триггер на `workflow_dispatch`
  с ручным подтверждением и environment protection.
- Не хранить `PYPI_API_TOKEN` в workflow; если токен уже был в логах/истории —
  отозвать и перевыпустить.
- Защитить теги: только maintainer может создать тег, запускающий publish.

**Приёмка.**

- в workflow нет job `publish` и ссылки на `PYPI_API_TOKEN`;
- `git tag v0.2.0 && git push origin v0.2.0` не создаёт run workflow
  (теги не входят в `on.push`);
- `gh run list` не показывает publish-run на тег;
- даже после будущего добавления `tags:` в триггер нет job, который публикует;
- случайный тег не может опубликовать пакет.

**Оценка:** 10 минут.

### 6.2. Пояснения

#### 6.2.1. Нет боевой оценки качества

`P1-2` в роадмапе честно признаёт: «6 критериев приёмки проверяют целостность
индекса, но не качество ответа». Замер 2026-11-02 — это **smoke**, а не eval:

- 8 запросов;
- релевантность по вхождению подстроки («максимов») в чанк;
- нет ground truth по страницам;
- нет recall@k, MRR, nDCG;
- нет answer correctness;
- нет статистической значимости.

Этого достаточно, чтобы найти «пустые режимы» и грубые провалы. Недостаточно,
чтобы ответить: «стало ли лучше после 45 фиксов?», «какой режим лучший?»,
«ухудшился ли граф после переиндексации?».

#### 6.2.2. 23 режима — лаборатория, а не продукт

После исправлений 11 режимов дают 8/8. Остальные 12 делятся на:

- **специализированные** — 9/10/11 (нужен знак), 22/23 (нужна зона), 20
  (ищет предложения) — для них нужен честный отказ или пояснение в меню;
- **недобирающие** — 12 (BM25 вместо dense), 21 (отказ LLM), 19/14/18 (частично).

Продукт не может предлагать пользователю 23 кнопки без объяснения. Нужен
**роутер**: система сама определяет тип запроса и выбирает 1–3 режима.
Остальные 20 — в «экспертный» раздел.

#### 6.2.3. Нет бюджета latency

| Режим | Время | Комментарий |
|---|---|---|
| 18 Qwen+FRIDA | **97,3 с** | самый долгий |
| 21 DAT+LLM | **41,9 с** | |
| 19 GraphRAG | **29,7 с** | |
| 12 Self-RAG | **22,1 с** | |
| 7 HyDE | **20,5 с** | |
| 17 LLM-фильтр | **10,3 с** | |
| 20 Sentence-level | **9,9 с** | |
| 2 Граф | **1,0 с** | лучший по скорости/качеству |
| 5 BM25+CE-ru | **2,4 с** | |
| Загрузка индекса | **7,4 с** | |
| Полный прогон 23 режимов | **≈4,5 мин** | машинное время |

Для интерактивного поиска 97 с — это отказ пользователя. Нужны:

- p95 default ≤ 10 с;
- LLM-режимы ≤ 30 с;
- всё, что > 30 с — помечено «экспериментальный» и выключено по умолчанию;
- кэш эмбеддингов, ответов, query expansion;
- параллельные вызовы.

#### 6.2.4. Граф перекошен в synonymy

736 089 рёбер, из них 726 250 — synonymy. Это **98,7 %**. PPR по такому графу
может «размываться»: масса случайных связей между похожими сущностями
конкурирует с реальными фактами.

Нужен ablation:

- с synonymy / без synonymy;
- `synonymy_edge_topk` и порог 0,8;
- влияние на recall@10 и latency.

Возможно, окажется, что synonymy помогает recall, но вредит точности. Сейчас
это не измерено.

#### 6.2.5. Данные не воспроизводимы

- PDF лежат в `data/`, который в `.gitignore`.
- `outputs/` в `.gitignore`.
- Нет sample-индекса (хотя бы 100 чанков) для CI и нового разработчика.
- Нет `HOW_TO_RUN.md`.
- Нет manifest индекса: версия, модель, дата, хеши PDF.

Следствие: **индекс нельзя восстановить из репозитория**. Через месяц вы не
вспомните, какой моделью и на каких PDF он построен.

#### 6.2.6. CI дорогой и устаревший

- 9 test-jobs: 3 OS × 3 Python. Для проекта, который реально работает на
  Windows + LM Studio, macOS-джобы почти бесполезны.
- `actions/upload-artifact@v3` и `download-artifact@v3` — GitHub вывел v3 из
  обращения; job упадёт на upload, даже если тесты пройдут.
- `codecov/codecov-action@v3` — устарел.
- `actions/setup-python@v4` — работает, но v5 актуален.
- `security` job: `bandit ... || true`, `safety check ... || true` — **всегда
  зелёный**, то есть не ворота, а декорация.
- Нет `timeout-minutes`, нет `concurrency`, нет `paths-ignore` для docs.
- `lint` гоняется в 3 копиях (3 Python), хотя результат одинаковый.

На private-репо минуты из пула Free (~2 000/мес). Один пуш = 2–3 часа машинного
времени. Несколько пушей в день — и лимит исчерпан.

**Факт на 2026-11-02:** лимит уже исчерпан. GitHub Actions не запускает job'ы

Это не «CI красный из-за тестов», а «CI не работает вообще». Пока billing не

#### 6.2.7. Ветка `develop` мертва

`main` впереди `origin/develop` на **81 коммит** и отстаёт на **2**. CI при этом

- ложное ощущение «две ветки»;
- лишние прогоны;
- риск смерджить устаревшее.

Решение: либо удалить `develop`, либо сделать её актуальной и ввести правило
«фича → PR в develop → main». Сейчас — удалить.

#### 6.2.8. Идентичность пакета

См. §5.5. Добавлю только: `README.md` — upstream-ный, и `pyproject.toml`
указывает `readme = "README.md"`. То есть **даже если** опубликовать пакет,
страница PyPI будет описывать HippoRAG 2 от OSU, а не ваш продукт.

#### 6.2.9. Нет наблюдаемости

### 9.2. H1 — «Качество и один лучший режим» (1–2 недели, P1)

**Цель:** доказать, что поиск стал лучше, и дать пользователю один понятный

#### Задача H1-1. Eval-база (первая, а не вторая)

- **Сценарий пользователя (0,5 ч, владелец) — до разметки.** Один абзац: кто
  спрашивает, какие вопросы задаёт, что считается правильным ответом. Без этого
  ground truth измеряет представление разработчика, а не потребность
  пользователя. Записать в `README_RU.md`; метрики ссылаются на него.
- **30–40 русских вопросов**, а не 50–60: это ручная разметка, её нельзя
  распараллелить и нельзя оценивать в «днях разработки». 3 класса:
  библиография, домен, перефразировка; внутри — подтипы («знак → зона»,
  определения, списки, сравнения, число гуа, «где в квартире»).
- Ground truth: `source_file`, `page_num`, эталонный ответ. Разметка —
  **вручную** (владелец/предметник), а не LLM-судьёй. LLM-судья — только после
  ручного эталона и проверки сходимости ≥ 0,8.
- Метрики:
  - `recall@5` по документам **и** по страницам;
  - `MRR@10`;
  - доля осмысленных ответов (answer adequacy);
  - доля отказов (refusal rate) и доля пустых ответов;
  - p50/p95 latency;
  - `nDCG@10` — опционально, если нужен единый ranking-показатель.
- Скрипт `scripts/eval_search_quality.py`, запускаемый на любом индексе.
- Baseline «до» — режим 2 «Граф» на бэкапе
  `outputs/_backup_20260514_pre_audit/`.
- Таблица «до/после» в `docs/INDEXING_GUIDE.md`.
- **Стоимость прогонов:** 23 режима × 30–40 вопросов — это ~700–900 прогонов,
  на LLM-режимах (10–42 с) — часы. Поэтому полный набор 23 режимов гонять на
  подмножестве (10–15 вопросов), а 2–3 режима-кандидата — на всех 30–40.
- **LLM-зависимые режимы (1, 12, 19, 21) — отдельная методика** (замечание
  Mavis, П-3): замерять retrieval-часть **до** LLM-вызова; LLM-ответы сравнивать
  по структуре и фактам, а не по тексту; фиксировать модель, версию, `temperature=0`
  и признак «LM Studio загружена». Иначе «до/после» будет измерять недетерминизм
  LLM, а не retrieval.
- **Вырожденный `min_max_normalize`** (замечание Mavis, П-3): при 1–2 кандидатах
  `range=0` → все получают 1.0. Фиксировать `n` кандидатов в отчёте и не
  сравнивать режимы с разным `n`; для `n<3` — не нормировать или fallback 0.5.

**Приёмка:** сценарий пользователя записан; скрипт работает; таблица есть;
baseline зафиксирован; для LLM-режимов есть отдельный retrieval-замер и
зафиксированы условия LLM; разметка ручная, 30–40 вопросов, LLM-судья не

### 10.2. Как не обмануть себя

1. **Ground truth — из корпуса, а не из памяти.** Эталон должен быть проверен
   по PDF, иначе eval измеряет вашу уверенность, а не качество.
2. **Релевантность — по страницам, а не по подстроке.** Подстрочный критерий
   («чанк содержит „максимов“») завышает recall.
3. **Считать всю выдачу, а не top-1.** Top-1 красив, но пользователь смотрит
   список.
4. **Фиксировать индекс и модель.** Eval на разных индексах несравним.
5. **Разделять retrieval и generation.** Если ответ неверный, сначала проверьте,
   попал ли нужный чанк в top-k.
6. **Считать пустые ответы отдельно.** «Честный отказ» и «пустота» — разные вещи.
7. **Не сравнивать «до/после» на разных вопросах.** Один и тот же набор.
8. **LLM-режимы — отдельно.** Для режимов 1, 12, 19, 21 замерять retrieval до
   LLM-вызова; ответы сравнивать по структуре и фактам, а не по тексту.
9. **Фиксировать `n` кандидатов.** При `n<3` `min_max_normalize` вырождается
   (`range=0` → все 1.0); не сравнивать режимы с разным `n`.
10. **Цитата — не украшение.** Ответ без проверяемой цитаты считается отказом,
    а не «правильным по смыслу»; факты вне корпуса — дефект, а не стиль (H2-6).

### 14.6. П-3. `min_max_normalize` и LLM-режимы

**Принято, оба подпункта.**

1. **Вырожденная нормировка.** При `n=1` или `n=2` кандидатах `range=0`, и
   `min_max_normalize` возвращает `ones` — все получают 1.0. Для `top_k=5`
   с отфильтрованным списком это делает скор неинформативным. В H1-1 добавлено:
   фиксировать `n` кандидатов в отчёте; не сравнивать режимы с разным `n`;
   для `n<3` — не нормировать или использовать fallback 0.5. Это **известное
   ограничение**, а не баг: менять поведение без eval рискованно.

2. **LLM-зависимые режимы.** Режимы 1 (reformulate), 12 (Self-RAG), 19
   (GraphRAG), 21 (DAT+LLM) зависят от состояния LM Studio и недетерминизма
   даже при `temperature=0`. Для них в H1-1 добавлена отдельная методика:
   - замерять retrieval-часть **до** LLM-вызова;
   - сравнивать ответы по структуре и фактам, а не по тексту;
   - фиксировать модель, версию, `temperature=0`, признак «LM Studio загружена»;
   - не требовать побитового совпадения.

Иначе «до/после» будет измерять дрожание LLM, а не улучшение поиска.
