## 2. Блокирующие возражения

### ⛔ Возражение 1. Пакет `astro_search/` должен лежать в `src/`, иначе он не попадёт ни в установку, ни в дистрибутив

**Что в плане:** раздел 2 — `astro_search/` на верхнем уровне репозитория, рядом с `main.py`.

**Что показала проверка:**

| Артефакт | Фактическое содержимое |
|----------|----------------------|
| editable-установка (`__editable__.hipporag-2.0.0a4.pth`) | добавляет в `sys.path` **ровно один** путь: `C:\Users\User\PycharmProjects\hipporag\src` |
| собранный wheel (`pip wheel . --no-build-isolation`) | top-level: **`['hipporag', 'hipporag-2.0.0a4.dist-info']`** — 72 модуля, из них ни одного `astro_search` |
| `pyproject.toml` | секции `[tool.setuptools]` / `packages` **нет** → работает auto-discovery setuptools в режиме src-layout, который смотрит **только** в `src/` |

**Последствия (проверяемы):**

1. `main.py` в корне делает `from astro_search.cli import main`. Это сработает **только** при запуске из корня репозитория (cwd попадает в `sys.path`). Из любой другой директории — `ModuleNotFoundError: No module named 'astro_search'`.
2. В wheel/sdist пакет `astro_search` **не попадёт вообще** → установка из дистрибутива останется без CLI, а `pip install -e .` из другой директории — без CLI тоже.
3. **Точки входа сломаются** — а это прямое требование плана (§5.4). Из 15 standalone-скриптов **8 полагаются на установленный пакет** (вставляют в `sys.path` несуществующий `tests/standalone/src` — такого каталога нет, поэтому фактически работает только установленный `hipporag`), и **7** — на корень/cwd. Первые восемь после переноса не найдут `astro_search`.

**Рекомендация.** Положить пакет в `src/`:

```
src/astro_search/          # вместо astro_search/ в корне
```

Тогда auto-discovery src-layout подхватит **оба** пакета (`hipporag` и `astro_search`), а `main.py` в корне останется тонкой точкой входа (`from astro_search.cli import main`) и будет работать при любом cwd — потому что `src/` уже прописан в editable-установке.

Альтернатива — явная конфигурация:
```toml
[tool.setuptools.packages.find]
where = ["src", "."]
```
Она работоспособна, но хрупка: придётся следить за каждым новым подпакетом и рисковать двойным включением (`hipporag` и `src.hipporag`). **Рекомендую `src/`.**

### ⛔ Возражение 2. `data/synonyms.json` попадёт под `.gitignore` — словарь не уедет в репозиторий

**Что в плане:** раздел 2 — `synonyms.py`: «`SYNONYM_MAP` → перенос в данные (`data/synonyms.json`)»; шаг 1 — «самая "мясистая" константа (~100 строк) уходит из кода в данные».

**Что показала проверка:**

```
.gitignore:20:data/
$ git check-ignore -v data/synonyms.json
.gitignore:20:data/    data/synonyms.json      → exit 0 (БУДЕТ ИГНОРИРОВАТЬСЯ)
```

Каталог `data/` сейчас занят локальными данными (`questions.txt`, `test_astrology.json`, три PDF корпуса) и целиком игнорируется.

**Последствие — тихое деградирование.** Свежий клон не получит словарь → `load_synonyms()` вернёт пусто → `_expand_query` не даст ни одного синонима → **keyword-expansion перестанет работать во всех 23 режимах**. При этом:
- юнит-тесты пройдут (они работают с fixtures, а не с файлом на диске);
- приёмка «снапшот выдачи до/после» упадёт на **сравнении** с эталоном, но только если эталон снят в том же окружении — то есть проблема обнаружится не сразу, а при работе на другой машине;
- это ровно тот класс дефектов, который мы весь цикл вычищали: **тихое искажение результата при зелёных тестах**.

**Рекомендация.** Положить словарь **внутрь пакета** — `src/astro_search/data/synonyms.json`: он попадёт и в git, и в wheel, и в sdist, и не конфликтует с `data/` корпуса.

Если путь `data/` принципиален, `.gitignore` надо переписать так, чтобы каталог игнорировался, а файл — нет:
```
data/*
!data/synonyms.json
```
(строка `data/` исключает **каталог целиком**, и `!data/synonyms.json` внутри неё не сработает — сначала нужно `data/*`, а не `data/`).

## 3. Существенное возражение

### ⚠️ Возражение 3. Единая сигнатура `fn(hipporag, query, top_k=10)` не соответствует реальным сигнатурам и тихо меняет поведение двух режимов

**Что в плане:** §1.3 — «**Единая сигнатура режима**: `fn(hipporag, query, top_k=10) -> list[Result]`. Режимы, которым нужны нестандартные параметры, оборачиваются `functools.partial`».

**Что показал AST-разбор 22 функций режимов:**

**(а) Пять функций `top_k` не принимают вообще** — `partial` их не спасёт, он передаст `top_k=10` → `TypeError`:

| Функция | Фактическая сигнатура |
|----------|----------------------|
| `search_with_llm_filter` | `(hipporag, query)` |
| `search_graphrag_agent` | `(hipporag, query)` |
| `extract_sign_full` | `(hipporag, query)` |
| `extract_sign_polished` | `(hipporag, query)` |
| `extract_sign_summary` | `(hipporag, query)` |

Нужны **адаптеры-обёртки**, а не `partial`.

**(б) У двух режимов другой дефолт `top_k`** — и реестр его тихо сломает:

| Функция | Сейчас | Станет при едином `top_k=10` |
|---------|--------|-------------------------------|
| `search_self_rag` | `top_k=30` | **10** — выдача урежется втрое |
| `search_semantic_filter` | `top_k=50` | **10** — вырежется впятеро |

Сейчас меню вызывает `search_fn()` **без** `top_k` (`main.py:3489-3497`), то есть каждый режим использует свой дефолт. Реестр с принудительным `top_k=10` это различие сотрёт.

**Рекомендация.** Не приводить сигнатуры к единой, а вынести `top_k` в отдельное поле реестра:

```python
@dataclass(frozen=True)
class ModeSpec:
    label: str
    fn: Callable          # вызывается как fn(hipporag, query) — дефолты остаются свои
    star: bool = False
    special: str = ""
    top_k: int | None = None   # None → не передавать, использовать дефолт функции
```

Для пяти функций без `top_k` — тонкие адаптеры в `modes/` (например `def _mode_graphrag(h, q): return search_graphrag_agent(h, q)`).

## 4. Методические замечания (не блокируют)

### 4.1. Оценка «1,5–2 рабочих дня» занижена

Приёмка §5.3 требует «поочерёдный прогон всех 23 режимов» **после каждого** из 7 шагов. Измеренная фактическая длительность одного режима: `extract_sign_polished` — ~113 последовательных LLM-вызовов (~2 мин), `search_qwen_frida` — ~131 с, LLM-режимы — 10–42 с. Полный прогон 23 режимов на одном запросе — **12–20 мин**; × 7 шагов — **1,5–2,5 ч только на smoke**, плюс сам перенос и отладка.

Реалистичная оценка: **3–5 рабочих дней**. Либо сократить smoke до **затронутых** режимов на каждом шаге (логично и в разы быстрее), либо заложить 3–5 дней.

### 4.2. Имя пакета `astro_search` при содержимом «поиск + QA-кэш + CLI»

Низкий приоритет, но `astro_search` с `qa_cache.py` и `cli.py` внутри вводит в заблуждение. Достаточно, чтобы подумать, что это только поиск.
