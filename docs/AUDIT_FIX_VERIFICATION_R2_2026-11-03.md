## 3. Проверка корректности — по каждому пункту

### 3.1 N1 (не-ASCII ключ больше не роняет сервер) — ✅ корректно

HTTP-прогон с `API_KEY=секретный-ключ`:

| Запрос | Раунд 1 | Раунд 2 |
|---|---|---|
| без ключа | `TypeError` → **500** | **401** ✅ |
| с ASCII-ключом | `TypeError` → **500** | **401** ✅ |

В логе сервера необработанных исключений нет. Сравнение по байтам корректно и для ASCII, и для UTF-8 — `compare_digest` работает с любыми байтами.

### 3.2 N2 (CORS-заголовки на 401) — ⚠️ частично

Заголовки в ответе 401 появились, и браузер с origin `http://localhost:3000` теперь видит причину отказа. Но origin **задан константой**, а не выведен из запроса, из-за чего второй разрешённый origin не работает:

| Origin запроса | `Access-Control-Allow-Origin` в 401 | Итог для браузера |
|---|---|---|
| `http://localhost:3000` | `http://localhost:3000` | ✅ совпадает, ошибка читается |
| `http://localhost:8000` | `http://localhost:3000` | ❌ **не совпадает** — ответ не читается, клиент видит CORS-ошибку вместо «нужен ключ» |
| `https://evil.example.com` | `http://localhost:3000` | не читается (свой origin не совпал) — утечки нет |

Второй origin (`http://localhost:8000`) входит в `allow_origins` CORS-конфигурации, то есть поддерживается для успешных запросов — но для отказа авторизации он не работает. Дублирование списка origin в двух местах (CORS-конфигурация и хардкод в guard) создаёт риск расхождения при правках.

**Рекомендуемый фикс (вместо хардкода):** зарегистрировать `CORSMiddleware` **после** guard, чтобы CORS оказался внешним слоем и сам добавлял заголовки ко всем ответам, включая 401 — тогда список origin останется в одном месте. Либо вычислять origin из запроса против `allow_origins`.

`import secrets` перенесён в шапку файла. Побочный эффект положительный: стоимость импорта на каждый запрос исчезла.
