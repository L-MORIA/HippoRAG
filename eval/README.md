# Eval-база: разметка и замер качества поиска (H1-1)

Здесь лежит датасет с ручной разметкой и правила, по которым считается
«до/после». Скрипт замера — `scripts/eval_search_quality.py`, метрики —
`src/astro_app/evaluation.py`.

## Зачем ручная разметка

Эталон (`source_file`, `page_num`, ответ) пишет владелец/предметник. LLM-судья
как источник истины не используется: он измеряет совпадение с собственной
моделью мира, а не потребность пользователя. LLM-судья допустим только
*после* ручного эталона и только если его согласие с ручной оценкой ≥ 0,8 —
и тогда он ускоряет разметку новых вопросов, но не заменяет её.

## Формат файла

`eval/dataset/questions.jsonl` — один вопрос на строку (JSONL удобнее ручной
правки: битая строка не ломает весь файл). Поддерживается и `.json` с массивом.

| Поле | Обязательно | Что это |
|---|---|---|
| `qid` | да | Уникальный id: буквы/цифры/`_`/`-`, 2..64 символа |
| `question` | да | Вопрос так, как его задал бы пользователь |
| `kind` | да | `bibliography` \| `domain` \| `paraphrase` |
| `subtype` | нет | `sign-zone`, `definition`, `list`, `comparison`, `gua-number`, `where-in-flat`, `title-author`, `edition`, `other` |
| `source_file` | да | Имя PDF, как в индексе (`source_file` чанка) |
| `page_num` | да/`null` | Страница с ответом; `null` — вопрос только в документных метриках |
| `reference_answer` | да | Эталонный ответ **(руками)** |
| `expected_terms` | желательно | 2–4 ключевых слова для adequacy; без них adequacy не считается |
| `status` | да | `draft` — черновик, `verified` — ручная разметка |
| `notes` | нет | Пометки, откуда взят ответ |

Строгие правила (специально, чтобы ошибки не «портили» метрики молча):

* неизвестное поле — ошибка (опечатка `sourse_file` иначе даёт recall = 0);
* `kind`/`subtype`/`status` вне списка — ошибка;
* `source_file`/`page_num`, которых нет в индексе — ошибка при проверке против
  индекса (`--validate-only` читает parquet, модели не грузит);
* пустые `question`/`reference_answer` — не ошибка, а «заготовка»: она
  пропускается и показывается в отчёте как `incomplete`.

## Объём и классы

Цель — **30–40 вопросов**: 10–15 библиография, 10–15 домен, 10–15
перефразировка. Меньше 30 — предупреждение в валидации, метрики приёмки
неполные. `status: verified` ставит только человек; `draft` в метрики по
умолчанию не идёт (его включает `--include-draft`, это только для smoke).

**Текущее состояние (2026-11-03):** 40 вопросов, все `verified`
(библиография 11, домен 15, перефразировка 14). Вопросы и эталоны
подготовлены ассистентом по тексту книг, владелец проверил и правил вручную.
Сводка на правку — `eval/dataset/REVIEW.md`. Baseline «до/после» —
`docs/INDEXING_GUIDE.md` § «До/после».

## Как заполнять

```bash
# 1. Посмотреть, что реально есть в индексе (по страницам документов)
python scripts/eval_bootstrap_dataset.py --per-source 4
#    → eval/dataset/candidates.jsonl (не коммитится): source_file/page
#      подставлены, question/reference_answer пустые, в notes — начало страницы

# 2. Переписать выбранные заготовки в eval/dataset/questions.jsonl,
#    заполнить question/reference_answer/expected_terms, поставить verified

# 3. Проверить разметку против индекса (быстро, без моделей)
python scripts/eval_search_quality.py --validate-only
```

## Как мерить

```bash
# baseline «до»: режим 2 «Граф» на бэкапе pre-audit
python scripts/eval_search_quality.py \
  --index outputs/_backup_20260514_pre_audit --modes 2 \
  --out outputs/reports/eval_before_mode2.json

# кандидаты на текущем индексе
python scripts/eval_search_quality.py --modes 2,5,20 \
  --out outputs/reports/eval_after.json --markdown-out outputs/reports/eval_after.md
```

Метрики: `recall@5` по документам и страницам, `MRR@10`, `nDCG@10` (бинарная
релевантность), отказы/пустые ответы, adequacy, p50/p95 latency. Таблица для
`docs/INDEXING_GUIDE.md` печатается в конце прогона.

### Почему документных метрик мало

В индексе три книги, поэтому recall@5 по документам почти всегда 1.0 —
достаточно одного чанка из нужной книги. Рабочая метрика — **recall@5 по
страницам**: попал ли режим на страницу с ответом.

### LLM-режимы (1, 7, 10, 11, 12, 17, 18, 19, 21)

Отдельная методика (план §9.2):

* в отчёт пишутся модель, `base_url`, `temperature` **из перехваченных
  запросов** (режимы ходят в LLM напрямую через `httpx.post`), число вызовов и
  суммарное время внутри них;
* `retrieval_ms` = время вне LLM-вызовов, то есть поиск без недетерминизма
  модели;
* ответы режимов 9–12, 19, 21 оцениваются по `expected_terms` (adequacy) и на
  отказы, а не по совпадению текста;
* если LM Studio недоступна, скрипт **отказывается** запускать такие режимы
  (таймаут вызова 300 с). `--stub-llm` подменяет ответы модели — это проверка
  механики, а не качества, и в отчёте помечается.

### Вырожденная нормировка

При 1–2 кандидатах `min_max_normalize` возвращает всем 1.0 (`range == 0`),
поэтому режимы с разным `n` кандидатов сравнивать нельзя. В отчёте на каждый
режим выводятся `n_candidates.mean/min/max` и число прогонов с `n < 3`.
